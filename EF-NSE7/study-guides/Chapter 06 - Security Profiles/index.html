Chapter Overview

SSL/TLS Inspection

The majority of web traffic today is encrypted with TLS — which means a firewall that can only see the outer envelope of packets is essentially blind to the payload. FortiGate solves this with SSL/TLS inspection: the firewall acts as a man-in-the-middle, decrypting traffic so security profiles can inspect the content, then re-encrypting and forwarding it. Two modes exist: certificate inspection (checks the server certificate and SNI only — fast, no content decryption) and deep SSL inspection (full decryption and inspection, requires distributing the FortiGate's CA certificate to clients).

FortiGate uses SNI (Server Name Indication) — the hostname the client sends in the TLS ClientHello — to match URL filter categories even before the certificate is seen. SAN (Subject Alternative Name) fields in certificates list all valid hostnames, allowing FortiGate to identify wildcard services. For deep inspection, FortiGate re-signs the server certificate with its own CA — clients must trust this CA to avoid browser certificate warnings. SSH deep inspection similarly inspects SSH tunnels for file transfers and command execution.

Web Filter, App Control & ISDB

Web Filter categorizes URLs and FQDNs using FortiGuard's category database — over 75 categories covering everything from gambling and adult content to cloud storage and business. Each category can be allowed, blocked, monitored, or warned. URL overrides let you whitelist or blacklist specific sites regardless of category. SafeSearch enforcement pushes conservative filtering to Google, Bing, and YouTube without blocking them entirely.

Application Control identifies applications using deep packet inspection of protocol signatures, regardless of port or encryption. The ISDB (Internet Service Database) extends this to entire internet services — Microsoft 365, AWS, Netflix, etc. — by maintaining curated lists of IP ranges and FQDNs for each service. ISDB entries can be used directly in firewall policies as destination objects, enabling policy rules like "allow Microsoft 365 traffic only during business hours." Both flow-based and proxy-based inspection modes are supported, with proxy-based offering deeper inspection at the cost of higher latency.

Mode selection: Flow-based inspection uses IPS engine scanning in a single pass — lower latency, suitable for most deployments. Proxy-based inspection buffers the full request/response before scanning — higher accuracy for antivirus and data loss prevention, but adds latency and memory overhead.

IPS & UTM Profiles

IPS (Intrusion Prevention System) inspects traffic against a database of known exploit signatures and behavioral heuristics. Each IPS sensor is a collection of signature filters — you can select by severity, target, protocol, or individual signature ID. Signatures rated critical or high default to block; lower severities default to monitor. False positives — legitimate traffic incorrectly flagged — can be addressed by creating signature overrides that set specific signatures to pass or monitor.

Botnet C2 blocking uses FortiGuard threat intelligence to block outbound connections to known command-and-control infrastructure — this catches compromised hosts before they can exfiltrate data or receive attacker commands. Protocol port mapping tells the IPS engine which application protocol to expect on non-standard ports — for example, if a custom app runs HTTP on port 8080, mapping it ensures HTTP signatures are applied. Combining IPS, web filter, application control, antivirus, and DNS filter into a UTM policy creates layered defense that inspects traffic at multiple levels in a single pass.
