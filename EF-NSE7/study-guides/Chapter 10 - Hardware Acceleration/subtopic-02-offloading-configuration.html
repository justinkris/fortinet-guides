Offloading Configuration

Configure hardware acceleration on FortiGate — VDOM link acceleration, IPsec offload, DVLAN/VXLAN support, and the NTurbo/IPSA settings that control how traffic reaches the fast path.

Knowing the hardware exists is not enough — you must configure it correctly or traffic silently falls back to the slow path.

The exam tests CLI commands for enabling/disabling offload, the NPU-flag values for IPsec SAs, and the conditions that prevent NP offload.

💭 THINK FIRST · VDOM LINK ACCELERATION

Inter-VDOM traffic on FortiGate passes through virtual links (npu_vlink interfaces). By default, these links are assigned to the root VDOM — meaning inter-VDOM traffic goes through the CPU. Offloading requires reassigning the two sides of a VDOM link to the two different VDOMs that need to communicate.

  • Why does inter-VDOM traffic go through the CPU by default even when the FortiGate has NP7 processors?
  • What is the naming convention for NPU VDOM link interfaces, and how do you validate that inter-VDOM traffic is actually being offloaded after configuration?
Q1 — MODEL ANSWER
By default, NP processors include VDOM link interfaces but they are all assigned to the root VDOM. Since both sides of the virtual link belong to root, inter-VDOM traffic has nowhere to go except the CPU for routing decisions. To offload, you must split the VDOM link pair — assign npu_vlink0 to VDOM A and npu_vlink1 to VDOM B — so the NP can forward traffic between them on the fast path.
Q2 — MODEL ANSWER
The naming convention is npu_vlink0 and npu_vlink1 (one pair per NP). After assigning each to a different VDOM and creating firewall policies, run "diagnose sys session list" and check the npu_info field. An offload code of 9/9 (for NP7) confirms hardware acceleration is active. If you see no_offload or disabled-by-policy, the configuration needs review.
SECTION 01

VDOM Link Acceleration via NPU Vlinks

npu_vlink0 assigned to VDOM A, npu_vlink1 assigned to VDOM B — inter-VDOM traffic offloaded through NP7.

Flat colorful illustration: two boxes at top labeled "VDOM A" (blue) and "VDOM B" (green). Below them, a large NP7 chip. Two virtual wire pairs labeled "npu_vlink0" and "npu_vlink1" connect each VDOM to the NP7. Traffic arrows show flow going from VDOM A, through NP7 (fast path), to VDOM B. FortiGate VDOM links that are associated with an NP processor can be accelerated. The NPU VDOM link interfaces use the naming convention npu_vlink0 and npu_vlink1. By default, all NP VDOM links are assigned to the root VDOM — this means inter-VDOM traffic travels through the CPU.

To enable hardware acceleration for inter-VDOM traffic, assign each side of an npu_vlink pair to a different VDOM:

  • Assign npu_vlink0 to VDOM A
  • Assign npu_vlink1 to VDOM B
  • Create firewall policies on both VDOMs using the npu_vlink interfaces

Once configured, the inter-VDOM traffic is accelerated through the NP processor, bypassing the CPU. You can also extend the number of accelerated inter-VDOM links by creating VLAN subinterfaces over the npu_vlink interfaces — each VLAN creates an additional accelerated path. The VLAN ID must match on both npu_vlink sides.

FortiGate CLI — Assign VDOM Link and Validate
# Assign npu_vlink interfaces to VDOMs
config system interface
    edit "npu0_vlink0"
        set vdom "VDOM_A"
        set ip 10.10.10.1 255.255.255.252
    next
    edit "npu0_vlink1"
        set vdom "VDOM_B"
        set ip 10.10.10.2 255.255.255.252
    next
end

# Validate acceleration is active
diagnose sys session list
# Look for: npu info: flag=..., offload=9/9 (code 9 = NP7)
Exam tip: To temporarily disable NP acceleration on a firewall policy for troubleshooting (e.g., to sniff traffic on npu_vlink), set auto-asic-offload disable in the firewall policy. Restore it to enable immediately after — leaving it disabled degrades performance for all traffic through that policy.
FortiGate CLI — Disable/Enable ASIC Offload per Policy
config firewall policy
    edit <policy_id>
        set auto-asic-offload disable   # default is enable
    next
end
🧠
MENTAL NOTE
npu_vlink0 + npu_vlink1 = one NP VDOM link pair. Default: both in root VDOM (no offload). Fix: assign one to each VDOM + create policies. Validate with diagnose sys session list → offload=9/9 for NP7. Disable per-policy with auto-asic-offload disable (troubleshooting only).

💭 THINK FIRST · DVLAN & VXLAN

Modern data center networks use Q-in-Q (double VLAN) tagging for provider/customer separation, and VXLAN for overlay networking. Without NP hardware support, every tagged frame would require the CPU to strip and re-add tags — at high traffic volumes this is expensive. NP7 and SP5 offload both.

  • What is the difference between 802.1AD and 802.1Q DVLAN modes, and which is the NP7 default?
  • How can you change the DVLAN mode on a specific NP7 processor rather than globally on all NPs?
Q1 — MODEL ANSWER
802.1AD uses an S-Tag (Service Tag) with ethertype 0x88A8 as the outer provider tag and a C-Tag (Customer Tag) with ethertype 0x8100 as the inner tag — this is the IEEE standard for Q-in-Q. 802.1Q double tagging uses 0x8100 for both tags. NP7 defaults to 802.1AD (ethertype 0x88A8), which is the service provider standard for carrier networks.
Q2 — MODEL ANSWER
Use the diagnose npu np7 dvlan-mode command with a specific device ID argument. Without the device ID, the command applies globally to all NP7 processors on the device. The SP5/NP7lite uses a similar command: "diagnose npu np7lite dvlan-mode." This per-NP granularity allows asymmetric configurations when different NP processors serve different network segments with different VLAN tagging schemes.

DVLAN and VXLAN Offloading

Flat colorful illustration: Ethernet frame breakdown from left to right. Sections labeled: "Dest MAC" (grey), "Src MAC" (grey), "S-Tag 0x88A8" (orange, wider, labeled "Provider VLAN"), "C-Tag 0x8100" (blue, labeled "Customer VLAN"), "EtherType" (grey), "Payload" (green). NP7 and SP5 (NP7lite) can offload 802.1AD and 802.1Q double VLAN (DVLAN) tagging as well as VXLAN encapsulation. By default, NP7 handles double VLAN frames using 802.1AD — the provider VLAN tag uses ethertype 0x88A8 (S-Tag) and the customer VLAN tag uses ethertype 0x8100 (C-Tag).

To view the current DVLAN mode setting:

FortiGate CLI — View and Change DVLAN Mode
# View current DVLAN mode on all NP7 processors
diagnose npu np7 dvlan-mode-list

# Change DVLAN mode (applies to all NP7 IDs if no dev-id specified)
diagnose npu np7 dvlan-mode 802.1Q          # for Q-in-Q with 0x8100 outer
diagnose npu np7 dvlan-mode 802.1AD         # for standard provider Q-in-Q
diagnose npu np7 dvlan-mode 802.1Q <dev-id> # per-NP7 processor ID

# On SP5/NP7lite devices:
diagnose npu np7lite dvlan-mode-list
diagnose npu np7lite dvlan-mode 802.1Q <dev-id>
Note: Both NP7 and SP5 also offload VXLAN encapsulated traffic. This enables hardware-accelerated overlay network forwarding — important in data center deployments where VXLAN is used for tenant separation.
🧠
MENTAL NOTE
NP7 default DVLAN = 802.1AD (S-Tag 0x88A8 outer). Change with: diagnose npu np7 dvlan-mode. SP5 uses np7lite in the command. Both NP7 and SP5 offload VXLAN. Per-NP mode change uses <dev-id> argument.

💭 THINK FIRST · IPSEC OFFLOADING

IPsec offloading to the NP involves the security associations (SAs) being copied from kernel memory into the NP processor's memory. The npu_flag field in the IPsec SA tracks this progress. A value of 00 means nothing is offloaded; 03 means both inbound and outbound SAs are in the NP — the ideal fully-accelerated state.

  • What does npu_flag=20 indicate, and what does that tell you about the IPsec configuration on that tunnel?
  • Why are SAs initially loaded to the kernel (npu_flag=00) before being copied to the NP, rather than going directly to the NP when phase 2 completes?
Q1 — MODEL ANSWER
npu_flag=20 indicates that the IPsec SA cannot be offloaded to the NP because the tunnel uses an unsupported cipher or HMAC algorithm. The tunnel is still functional — the CPU handles encrypt/decrypt in software — but there is no hardware acceleration benefit. The fix is to reconfigure the IPsec phase 1/2 to use algorithms supported by the NP hardware.
Q2 — MODEL ANSWER
SAs are created by the IKE daemon running on the CPU — it's a software process that negotiates and establishes the cryptographic parameters. The kernel is the natural first home for new SAs. The NP offload only makes sense after actual traffic arrives (first IPsec packet), because only then does the system confirm the SA is being used and worth copying to NP hardware. This lazy-copy approach avoids wasting NP SA table space on idle tunnels.
SECTION 03

IPsec Encryption Offloading and the NPU-Flag

📷 images/s3-ipsec-npu-flag.png

IPsec SA npu_flag values: 00 (kernel only) → 01 (outbound to NP) → 02 (inbound to NP) → 03 (both offloaded).

Flat colorful illustration: horizontal progression timeline. Four numbered stages: Stage 1 labeled "npu_flag=00" shows SA in CPU/kernel (grey). Stage 2 "npu_flag=01" shows outbound SA copied to NP (blue arrow pointing right to NP chip). Stage 3 "npu_flag=02" shows inbound SA copied (arrow pointing left back). Stage 4 "npu_flag=03" shows both SAs in NP (green checkmark). A separate red box shows "npu_flag=20 — Unsupported cipher, no offload possible." Pastel palette, bold outlines, educational infographic.

FortiGate can offload IPsec encryption and decryption to the NP hardware on supported models. The supported algorithms depend on the NP version and model. By default, hardware offloading is enabled for all supported algorithms. You can disable NP offload per IPsec tunnel with the npu-offload setting.

FortiGate CLI — IPsec NP Offload Control
# Disable NP offload for a specific IPsec tunnel (default: enable)
config vpn ipsec phase1-interface
    edit <tunnel_name>
        set npu-offload disable   # default is enable
    next
end

# Disable Diffie-Hellman ASIC offload globally (CP offload for DH exchange)
config system global
    set ipsec-asic-offload disable   # default is enable
end

Each IPsec SA has an npu_flag field that shows its current offload state. Use diagnose vpn tunnel list to inspect it:

npu_flag ValueMeaning
00Both IPsec SAs loaded to kernel only (tunnel up, no NP traffic yet or offload disabled)
01Outbound IPsec SA copied to NPU
02Inbound IPsec SA copied to NPU
03Both outbound and inbound SAs copied to NPU — fully accelerated
20Unsupported cipher or HMAC — IPsec SA cannot be offloaded to NP
Exam tip: npu_flag=20 means the cipher or HMAC used by the tunnel is not supported by the NP hardware — the tunnel still works via software (CPU), but there is no hardware acceleration. Change the phase 1/2 algorithms to NP-supported ciphers to fix this.
Note: Strict header checking (check-protocol-header strict) disables ALL NPs, CPs, and SPs globally — useful for testing but must never be left enabled in production. The default is loose.
FortiGate CLI — Strict Header Checking (disables all SPUs)
config system global
    set check-protocol-header loose   # default - basic header checks only
    # set check-protocol-header strict  # also checks ESP: seq num, SPI, data length
    #                                    WARNING: disables ALL NPs, CPs, and SPs
end
🧠
MENTAL NOTE
npu_flag: 00=kernel only, 01=outbound in NP, 02=inbound in NP, 03=both in NP (fully accelerated), 20=bad cipher (no offload). Disable per-tunnel with npu-offload disable. check-protocol-header strict kills ALL SPUs globally.

💭 THINK FIRST · NTURBO & IPSA CONFIG

NTurbo is enabled by default and distributes IPS sessions across multiple IPS engine processes. IPSA (IPS Acceleration) offloads the pattern matching itself to the CP hardware. These two features work together — NTurbo handles session distribution to IPS engines, IPSA offloads the heavy pattern matching from those IPS engines to the CP.

  • What is the difference between np-accel-mode and cp-accel-mode in the "config ips global" settings, and what does each control?
  • Why is cp-accel-mode set to "basic" on FortiGate devices with a single CP8 chip, while other devices default to "advanced"?
Q1 — MODEL ANSWER
np-accel-mode controls NTurbo behavior — whether the NP distributes IPS sessions to multiple IPS engine processes (basic = enabled load-balance approach, none = disabled). cp-accel-mode controls IPSA — whether and how much IPS pattern matching work is offloaded to CP hardware (basic = some offload, advanced = more types of pattern matching offloaded, none = all pattern matching stays on CPU). They are configured together under "config ips global."
Q2 — MODEL ANSWER
The CP8 has fewer parallel processing resources than CP9/CP10. "Advanced" mode tries to offload more pattern matching types, which on a single CP8 could create bottlenecks if the CP is overwhelmed. "Basic" mode offloads a safer subset of patterns that the CP8 can handle without becoming the performance bottleneck. On multi-CP or CP9/10 devices, "advanced" mode is safe and beneficial because there is more CP capacity to absorb the additional workload.
SECTION 04

NTurbo and IPSA Configuration

📷 images/s4-nturbo-ipsa.png

NTurbo (np-accel-mode) distributes sessions to IPS engines; IPSA (cp-accel-mode) offloads pattern matching to CP hardware.

Flat colorful illustration: NP7 chip at top left sending packets via NTurbo arrows to multiple "IPS Engine" CPU cores. Each IPS engine box has a small arrow pointing right to a CP10 chip labeled "Pattern Matching (IPSA)." The CP10 offloads pattern matching, returning results to IPS engines. Two labels: "np-accel-mode = basic/none" near NTurbo arrows, "cp-accel-mode = basic/advanced/none" near IPSA arrows. Pastel palette, bold outlines, no shadows, educational infographic.

NTurbo (configured via np-accel-mode) distributes flow-based IPS sessions across multiple IPS engine processes, improving IPS throughput. IPSA (configured via cp-accel-mode) offloads the actual IPS pattern matching to CP hardware, reducing CPU load further. Both are enabled by default.

FortiGate CLI — NTurbo and IPSA Configuration
# Configure NTurbo and IPSA acceleration modes
config ips global
    set np-accel-mode {none | basic}   # basic = default (NTurbo load-balance enabled)
    set cp-accel-mode {none | basic | advanced}  # advanced = default on most devices
    #                                              basic = default on devices with 1x CP8
end

# Disable NTurbo per-policy (for troubleshooting)
config firewall policy
    edit <policy_id>
        set np-acceleration {disable | enable}   # enable is default
    next
end

The cp-accel-mode controls IPSA behavior:

  • none — All pattern matching handled by CPU, no CP offload
  • basic — Redirects flow-based pattern matching requests to CP hardware (default on single-CP8 devices)
  • advanced — Offloads more types of pattern matching to CP; default on most devices with CP9/CP10
Exam tip: To disable NTurbo globally, set np-accel-mode none in config ips global. To disable per-policy, use np-acceleration disable in the firewall policy. Both are troubleshooting tools — leaving NTurbo disabled reduces IPS performance significantly.
🧠
MENTAL NOTE
config ips global: np-accel-mode = NTurbo (basic=on, none=off). cp-accel-mode = IPSA (none/basic/advanced). Advanced default on CP9/10 devices; basic default on single-CP8. Disable NTurbo per-policy: np-acceleration disable in firewall policy.

💭 THINK FIRST · BEST PRACTICES

Hardware acceleration and inspection mode are deeply intertwined. Proxy-based inspection never offloads to NP — making it incompatible with the fast path. SSL deep inspection is expensive but can be offloaded to CP hardware to reduce impact. The exam frequently tests when NP offload is blocked and what to do about it.

  • A firewall policy has both a flow-based IPS profile and a proxy-based web filter profile applied. Will this session be offloaded to the NP? Why or why not?
  • What are four specific conditions that prevent NP offload even when auto-asic-offload is enabled on the policy?
Q1 — MODEL ANSWER
No. A firewall policy with a mix of flow-based and proxy-based security profiles is never offloaded to the NP and is always processed by the FortiGate CPU. This is a hard rule — even one proxy-based profile in the policy removes the session from the fast path entirely. To maximize NP offload, security profiles must be exclusively flow-based in any policy that should benefit from hardware acceleration.
Q2 — MODEL ANSWER
The four conditions that prevent NP offload are: (1) NP acceleration disabled on the policy (auto-asic-offload disable); (2) the firewall policy includes proxy-based security profiles; (3) the firewall session requires a FortiOS session helper; (4) tunneling is enabled — traffic to/from a tunneled interface such as SSL VPN or GRE, except for IPsec VPN sessions which can still be offloaded.
SECTION 05

Hardware Acceleration Best Practices

📷 images/s5-best-practices.png

Flow-based inspection enables NP offload. Proxy-based forces CPU path. Mixed policy = always CPU.

Flat colorful illustration: three rows, each showing a firewall policy scenario. Row 1: "Flow-based only" → NP7 fast path (green checkmark). Row 2: "Proxy-based only" → CPU path (yellow warning). Row 3: "Mixed (flow + proxy)" → CPU path (red X, label "Never offloaded"). Each row shows a traffic arrow and the destination (NP chip vs CPU chip). Pastel palette, bold outlines, no shadows, educational infographic.

Hardware acceleration best practices help maximize throughput especially for entry-level FortiGate models serving as hubs in enterprise networks. The choice of inspection mode is the most critical decision:

Flow-based inspection is the default mode and allows NP offload for eligible sessions. It identifies and blocks threats in real time with lower resource usage. It is recommended for policies prioritizing throughput.

Proxy-based inspection buffers and fully reassembles traffic before inspecting it — enabling more thorough inspection and features like category usage quota. However, proxy-based sessions are never offloaded to the NP and always run through the CPU.

Sessions that will NOT offload to NP even with auto-asic-offload enabled:

  • NP acceleration is disabled on the specific firewall policy
  • Firewall policy includes any proxy-based security profile
  • Firewall policy includes a mix of flow-based and proxy-based profiles
  • Session requires a FortiOS session helper
  • Tunneling is enabled (SSL VPN, GRE — except IPsec VPN, which can offload)

SSL Deep Inspection best practices to minimize performance impact:

  1. Limit the number of policies that allow encrypted traffic requiring SSL inspection
  2. Deploy SSL inspection gradually rather than enabling it everywhere at once
  3. Apply SSL deep inspection only where truly needed — exempt known-trusted traffic
  4. Use hardware acceleration (CP9/CP10) to offload SSL processing to content processors
Exam tip: A policy with mixed profiles (any flow-based AND any proxy-based together) is ALWAYS processed by the CPU — NP offload is blocked by the presence of any proxy-based profile in the same policy.
🧠
MENTAL NOTE
4 NP offload blockers: (1) auto-asic-offload disabled, (2) proxy-based profile present, (3) session helper required, (4) tunnel (SSL VPN/GRE) — but NOT IPsec. Flow-based = offload eligible. Mixed policy = always CPU. SSL deep inspect: use CP hardware to minimize impact.
