💭 THINK FIRST · VIRTUAL CLUSTERING

Virtual clustering extends FGCP to environments with multiple VDOMs, enabling each cluster device to serve as primary for a different set of VDOMs simultaneously. This is a more nuanced form of HA than simply having one primary and one standby.

  • In VDOM partitioning, both FortiGate devices are active simultaneously — yet HA mode is set to active-passive. Why does active-passive make sense here, and what happens during a failover?
  • Virtual clustering is limited to 30 virtual clusters. What is the implication for environments with more than two FortiGates needing multi-VDOM HA?
Q1 — MODEL ANSWER
Active-passive means each VDOM has exactly one primary device at a time — there's no inter-VDOM load balancing of sessions. VDOM partitioning lets FGT1 be primary for VDOM A while FGT2 is primary for VDOM B. During failover, one device takes over processing all VDOMs, so the workload is not split — it's entirely on the surviving device until recovery.
Q2 — MODEL ANSWER
Environments needing more than two devices with multiple VDOMs cannot use virtual clustering directly. They must use FGSP standalone session synchronization, or design around the limitation by not putting multiple VDOMs in a single cluster beyond two members.
SECTION 01

Virtual Clustering & VDOM Partitioning

📷 images/s1-virtual-clustering.png

VDOM partitioning: FGT1 is primary for VDOM A, FGT2 is primary for VDOM B.

Flat colorful illustration: two FortiGate devices side by side. Each device shows two VDOM boxes (VDOM A in teal, VDOM B in coral). Left device shows VDOM A labeled "Primary" (bright) and VDOM B labeled "Secondary" (dim). Right device shows VDOM A "Secondary" (dim) and VDOM B "Primary" (bright). Arrow between devices labeled "Active-Passive HA". Bold outlines, pastel palette, no shadows.

Virtual clustering is an extension of FGCP for FortiGate devices with multiple VDOMs enabled. It operates in active-passive mode and allows each cluster device to act as the primary for a different subset of VDOMs — a technique called VDOM partitioning. The cluster is limited to a maximum of 30 virtual clusters and is only supported between two FortiGate devices.

In VDOM partitioning, traffic for each VDOM is processed by whichever device is primary for that VDOM. During a failover, the surviving device takes over as primary for all VDOMs. VDOM partitioning distributes normal load across both devices, but does not provide load balancing of individual sessions within a VDOM — that remains per-primary-device.

FortiGate CLI — VDOM Partitioning Configuration
# On NGFW-1 (primary for VDOM1, secondary for VDOM2)
config system ha
    set mode a-p
    set vcluster-status enable
    config vcluster
        edit 1
            set override disable
            set priority 200
            set vdom "VDOM1" "root"
        next
        edit 2
            set override disable
            set priority 50
            set vdom "VDOM2"
        next
    end
end

# On NGFW-2 (secondary for VDOM1, primary for VDOM2)
# set priority 100 for VDOM1, set priority 200 for VDOM2
Note: The maximum HA group ID for virtual clustering is 7 (compared to the standard HA maximum). Other requirements (model, firmware, license, disk) are the same as standard HA clusters.
🧠
MENTAL NOTE
Virtual clustering = FGCP + multiple VDOMs, active-passive only, max 30 virtual clusters, 2-device limit. VDOM partitioning distributes traffic by making each device primary for different VDOMs. Max group ID = 7. Highest priority per VDOM wins primary role for that VDOM.

💭 THINK FIRST · FGSP OVERVIEW

FGSP is fundamentally different from FGCP: it relies on external load balancers for traffic distribution and does not use a primary/secondary model for traffic processing. All devices operate as peers. This makes FGSP ideal for environments where network topology prevents FGCP from working effectively.

  • FGSP can support 2–16 standalone FortiGates or 2–16 FGCP clusters. Why might you use FGCP clusters as FGSP peers rather than standalone FortiGates?
  • What is the critical difference between FGSP's approach to load balancing vs FGCP's active-active mode?
Q1 — MODEL ANSWER
Using FGCP clusters as FGSP peers adds a second layer of redundancy: each FGSP "peer" is itself an HA pair. This means you get local failover within each FGCP cluster (device-level redundancy) AND cross-cluster session synchronization via FGSP. A standalone FortiGate peer has no local redundancy — if it fails, the load balancer must reroute all its sessions.
Q2 — MODEL ANSWER
In FGCP active-active, the primary controls all load balancing decisions — all traffic arrives at the primary first. In FGSP, an external load balancer makes distribution decisions and sends traffic directly to any peer. FGSP peers process their assigned sessions independently, with no internal primary controlling redistribution. FGSP is truly distributed; FGCP active-active is centralized-with-delegation.
SECTION 02

FGSP Overview and Topology

📷 images/s2-fgsp-topology.png

FGSP topology: external load balancers direct traffic to FortiGate peers; peers share session tables.

Flat colorful illustration: internal network on left feeding into an external load balancer, which connects to two FortiGate peer devices (Peer_1 and Peer_2) labeled with IP addresses. Peer devices connect to a second load balancer and then to the internet on the right. A dashed double-headed arrow between peers labeled "Session Sync". Bold outlines, pastel palette, teal/coral colors, minimal text.

The FortiGate Session Life Support Protocol (FGSP) is an HA solution focused exclusively on session sharing between peer FortiGate devices — it does not handle traffic distribution itself. Load balancing is performed by external network devices (load balancers), while FGSP ensures session tables are synchronized across all peers so that failover is seamless.

FGSP supports 2–16 standalone FortiGate devices or 2–16 FGCP clusters (two members each) as peers. Adding more devices increases CPU and memory overhead because all peers must stay synchronized. By default, FGSP synchronizes all IPv4 and IPv6 TCP sessions and IPsec tunnels. Additional session types require explicit configuration.

FortiGate CLI — Basic FGSP Configuration (Peer_1)
config system standalone-cluster
    config cluster-peer
        edit 1
            set peerip 10.10.10.1
        next
    end
    set standalone-group-id 1
    set group-member-id 1
end
Analogy

FGSP is like a relay team with a shared memory — any runner can pick up where the last left off, because they all know exactly what happened.

  • External load balancer — the coach deciding which runner starts each race
  • FGSP session sync — the shared mental map every runner carries, so handoffs are seamless
  • FGCP active-active — one coach AND one lead runner who hands off laps, not the coach directly

Exam tip: FGSP peers each need a unique IP address (unlike FGCP where virtual MACs abstract the addressing). The external load balancer must route all packets for a given session to the same peer whenever possible.

💭 THINK FIRST · SESSION SYNCHRONIZATION

FGSP session sync keeps all peers' session tables identical so that any peer can handle any packet of any session without disruption. But not all session types are synchronized by default — and how synchronization is secured matters in multi-datacenter deployments.

  • Why are UDP and ICMP sessions NOT synchronized by default in FGSP — and why might you want to enable connectionless session sync anyway?
  • When would you encrypt FGSP session synchronization traffic, and what is the mechanism used?
Q1 — MODEL ANSWER
UDP/ICMP are connectionless — they have no guaranteed delivery or established state, so the overhead of tracking them is usually not worth the benefit. However, some applications (VoIP, TFTP, DNS) depend on stateful UDP session tracking. Without syncing these sessions, a failover would drop all in-progress connectionless sessions, impacting real-time applications.
Q2 — MODEL ANSWER
When FGSP peers are in different datacenters, session sync traffic crosses untrusted network segments. Enabling encryption wraps the sync traffic in an IPsec tunnel — the tunnel and required firewall policies are automatically created when you enable the encryption setting and set a pre-shared key. Note: encryption only works for Layer 3 connections.

Session Synchronization Configuration

📷 images/s3-session-sync.png

Session types and sync configuration: TCP/IPsec by default, others require explicit config.

Flat colorful illustration: a two-column table-style infographic. Left column "Session Type" lists: TCP (teal, default), IPsec (teal, default), UDP (coral, needs config), ICMP (coral, needs config), NAT (coral, needs config), Expectation (coral, needs config). Right column shows CLI commands in dark boxes. Bold outlines, pastel palette, minimal text.

By default, FGSP synchronizes all IPv4 and IPv6 TCP sessions and IPsec tunnels. Additional session types must be explicitly enabled. The table below summarizes the available options:

Session TypeCLI Command
UDP and ICMP (connectionless)set session-pickup enable + set session-pickup-connectionless enable
Expectation sessions (SIP, FTP pinholes)set session-pickup-expectation enable
NAT sessionsset session-pickup-nat enable

Session synchronization can also be filtered — you can limit sync to traffic from specific source interfaces, destination interfaces, or IP address ranges using the session-syn-filter option under each cluster peer configuration.

For inter-datacenter deployments, FGSP session sync can be encrypted using an automatic IPsec tunnel. Enable encryption enable and set psksecret under config system standalone-cluster. The required IPsec VPN and policies are created automatically. Encryption is supported for Layer 3 connections only.

FortiGate CLI — Session Sync Options & Encryption
# Enable additional session types
config system ha
    set session-pickup enable
    set session-pickup-connectionless enable
    set session-pickup-expectation enable
    set session-pickup-nat enable
end

# Enable sync encryption (Layer 3 only)
config system standalone-cluster
    set encryption enable
    set psksecret fortinet
end

# Layer 2 session sync interface
config system standalone-cluster
    set session-sync-dev port4
end
🧠
MENTAL NOTE
Default sync: IPv4/IPv6 TCP + IPsec only. Must explicitly enable: connectionless (UDP/ICMP), expectation (SIP/FTP pinholes), NAT. Encryption uses auto-created IPsec tunnel — Layer 3 only. Layer 2 sync via session-sync-dev; falls back to Layer 3 if Layer 2 link fails.

💭 THINK FIRST · ASYMMETRIC TRAFFIC

Asymmetric routing — where forward and return packets traverse different firewalls — breaks stateful inspection unless the firewall that didn't see the first packet can obtain the session context. FGSP has two strategies for this depending on whether Layer 2 connectivity exists between peers.

  • In the Layer 2 asymmetric traffic use case, why does traffic "bounce" from FGT_2 back to FGT_1 instead of FGT_2 just inspecting it directly?
  • What does setting layer2-connection unavailable change about how FGSP handles asymmetric traffic in a cloud environment?
Q1 — MODEL ANSWER
FGT_2 did not see the first packet of the session — FGT_1 owns the session. For stateful security inspection (UTM/proxy), all packets of a session must be seen by the same device that processed the first packet. So FGT_2 forwards the asymmetric return packet back to FGT_1 using the MAC address of FGT_1's interface, allowing FGT_1 to apply security inspection on the complete session context.
Q2 — MODEL ANSWER
When layer2-connection is unavailable (cloud environments without Layer 2 adjacency), FGSP cannot use MAC-address forwarding to redirect packets. Instead, it encapsulates the asymmetric traffic in a UDP tunnel between FGSP peer interfaces (Layer 3 forwarding). FGT_2 wraps the packet and sends it to FGT_1's peer IP, where FGT_1 unwraps and inspects it.
SECTION 04

Asymmetric Traffic Inspection

📷 images/s4-asymmetric-traffic.png

Layer 2 vs Layer 3 asymmetric forwarding: traffic bounces to session owner for inspection.

Flat colorful illustration: two-panel layout. Left panel shows Layer 2 topology with FGT_1 and FGT_2 connected via switch, return traffic arrow from FGT_2 to FGT_1 labeled "MAC forward". Right panel shows Layer 3 topology with FGT_2 sending UDP-encapsulated packet to FGT_1 via router labeled "UDP tunnel". Pastel palette, bold outlines, minimal text.

When FGSP peers handle asymmetric traffic (forward path via Peer_1, return path via Peer_2), security inspection requires all packets of a session to reach the session owner — the device that processed the first packet. FGSP provides two mechanisms for this based on Layer 2 availability:

Use Case 2 — Layer 2 available: Set layer2-connection available. The peer that receives asymmetric traffic forwards it back to the session owner using the session owner's MAC address (Layer 2 forwarding). This requires both peers to be in the same subnet and have Layer 2 adjacency.

Use Case 3 — Layer 2 unavailable (default): Set layer2-connection unavailable. Asymmetric traffic is encapsulated in a UDP connection and forwarded through the peer interface to the session owner using Layer 3. This is the default behavior and works in cloud environments.

FortiGate CLI — Asymmetric Traffic Configuration
# Layer 2 asymmetric forwarding (peers directly connected)
config system standalone-cluster
    set standalone-group-id 1
    set group-member-id 1
    set layer2-connection available
    set session-sync-dev port1
end

# Layer 3 asymmetric forwarding (cloud / no L2, default)
config system standalone-cluster
    set standalone-group-id 1
    set group-member-id 1
    set layer2-connection unavailable
    unset session-sync-dev
end
Exam tip: layer2-connection unavailable is the default value. Layer 2 mode requires same-subnet interfaces and direct Layer 2 adjacency between FGSP peers. Cloud environments always use Layer 3 (UDP encapsulation).
🧠
MENTAL NOTE
Asymmetric traffic must return to session owner for UTM inspection. Layer 2 mode: MAC forwarding (same subnet required). Layer 3 mode: UDP encapsulation (cloud-compatible, default). layer2-connection is unavailable by default. Performance is better with symmetric traffic — UTM works in any case.

💭 THINK FIRST · FGCP VS FGSP COMPARISON

FGCP and FGSP are both Fortinet-proprietary HA solutions, but they solve different problems. Knowing which to deploy — and when FGSP complements an FGCP cluster — is a key exam skill. Configuration synchronization adds another layer of nuance.

  • FGSP configuration synchronization (standalone config sync) uses the same election process as FGCP. But in FGSP, what are the primary/secondary roles actually used for?
  • If you need more than 4 FortiGates in an HA deployment with session synchronization, which protocol must you use and why?
Q1 — MODEL ANSWER
In FGSP standalone configuration synchronization, the primary/secondary roles are only for configuration sync purposes — they do not control traffic processing. The device elected primary pushes configuration to the secondary, but both devices independently process their own sessions. This is unlike FGCP where the primary role also controls traffic distribution.
Q2 — MODEL ANSWER
FGCP is limited to 2–4 FortiGate devices in a cluster. For more than 4 devices with session synchronization, you must use FGSP, which supports up to 16 standalone FortiGates or 16 FGCP clusters. FGSP is the only Fortinet protocol that scales beyond 4 devices for session-aware HA.

FGCP vs FGSP Comparison

📷 images/s5-fgcp-fgsp-compare.png

Feature comparison: FGCP native redundancy vs FGSP external load balancer dependency.

Flat colorful illustration: two-column comparison infographic. Left column "FGCP" with teal header showing: 2-4 devices, native load balancing, native config sync, internal heartbeat. Right column "FGSP" with coral header showing: 2-16 peers, external load balancer, optional config sync, Layer 3 peer comms. Checkmarks and X marks. Pastel palette, bold outlines.

The following comparison table summarizes the key differences between FGCP and FGSP to help you select the right protocol for a given enterprise scenario:

FeatureFGCPFGSP
Redundancy capacity2–4 FortiGate devices2–16 standalone or 2–16 FGCP clusters
Load balancingNative (active-active); VDOM partitioning in A-PThrough external load balancer only
Session synchronizationAvailable via configurationAvailable via configuration
Configuration synchronizationNativeAvailable if required (standalone config sync)

Standalone configuration synchronization in FGSP works identically to FGCP config sync — it uses the same election process to select a primary device that pushes configuration. Enable it with set mode standalone and set standalone-config-sync enable. Primary/secondary roles in this mode are config-sync only — not traffic-processing roles.

FortiGate CLI — Standalone Config Sync
config system ha
    set group-id 1
    set group-name "Cluster1"
    set mode standalone
    set password fortinet1
    set hbdev "port2" 50 "port3" 50
    set standalone-config-sync enable
    set override disable
    set priority 200
end
Best practice: Use FGCP when you have control over the network topology and 2–4 devices are sufficient. Use FGSP when external load balancers are already in place, when you need more than 4 devices, or when asymmetric routing is unavoidable.
🧠
MENTAL NOTE
FGCP max: 4 devices. FGSP max: 16 standalone or 16 FGCP clusters. Only FGCP has native load balancing. FGSP config sync uses same election as FGCP — but primary/secondary roles are config-only, not traffic-processing. FGSP is compatible with VRRP.
