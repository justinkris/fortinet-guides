💭 THINK FIRST · HA REQUIREMENTS

Forming an HA cluster sounds simple — just connect two FortiGates. But FortiGate enforces strict preconditions before any cluster can operate. Understanding which requirements are hardware-level vs configuration-level is critical for both deployment and troubleshooting.

  • Why must all cluster members run the same firmware version? What happens at the protocol level if they don't match?
  • If two members have different FortiGuard licenses, what licensing level will the cluster use — and why is that a problem you might not notice immediately?
Q1 — MODEL ANSWER
Cluster members use FGCP to communicate, and FGCP relies on both devices understanding the same data structures and synchronization protocol. Mismatched firmware creates incompatible data formats for heartbeats and config sync, so the cluster simply won't form — or worse, it will form inconsistently and fail during a failover.
Q2 — MODEL ANSWER
The cluster resolves to the lowest licensing level among all members. So if only one member has FortiGuard Web Filtering purchased, no member in the cluster will support Web Filtering. This is a silent degradation — the feature appears enabled on one device but the cluster enforces the minimum, which can cause security gaps that aren't obvious until you inspect cluster status.
SECTION 01

HA Requirements

📷 images/s1-ha-requirements.png

Hardware and configuration requirements that must match across all cluster members.

Flat colorful illustration: two FortiGate devices side by side with a checklist overlay showing matching model, firmware, license, hard drive, and operating mode icons. Pastel palette (teal/coral/cream), bold outlines, minimal text labels, educational infographic feel. No shadows, no gradients.

To form an HA cluster, all members must share the same hardware model (or VM model), firmware version, licensing level, hard drive configuration (same number and size), and operating mode of the management VDOM. These are non-negotiable — a mismatch prevents cluster formation.

Licensing is especially tricky: if members have different FortiGuard subscriptions, the cluster uses the lowest licensing level among all devices. For example, purchasing Web Filtering for only one member means no member in the cluster supports Web Filtering once joined. VDOMs divide a physical FortiGate into additional logical devices — so the operating mode (NAT vs transparent) of the management VDOM must also match.

From a configuration perspective, all members need the same HA group ID, group name, password, and heartbeat interface settings. Best practice calls for at least two heartbeat interfaces in the same broadcast domain, providing redundancy if one heartbeat link fails. The cluster will fall back to the next heartbeat interface ranked by priority in the list.

FortiGate CLI — Basic HA Configuration
config system ha
    set mode a-p
    set group-id 10
    set group-name "Training"
    set password <password>
    set hbdev "port3" 10 "port4" 20
end
Exam tip: Use static IP configuration on DHCP or PPPoE interfaces during initial cluster setup. After the cluster forms, you can switch back. DHCP address conflicts during join can silently break the cluster.
🧠
MENTAL NOTE
5 things must match: model, firmware, license, hard drive, management VDOM mode. Licensing uses the lowest level. Configure at least 2 heartbeat interfaces. The hbdev priority value is higher = higher priority (not a cost metric).

💭 THINK FIRST · PRIMARY ELECTION

Every cluster needs exactly one primary. FortiGate uses a tiered election process with two different orderings depending on whether HA override is enabled. The subtle difference between these two modes has real consequences for failover behavior in production.

  • Override disabled is the default. In this mode, why does HA uptime take precedence over the configured priority — and how does running diagnose sys ha reset-uptime force a failover?
  • What is the key tradeoff of enabling HA override — specifically, what does the cluster do when the original primary comes back online?
Q1 — MODEL ANSWER
Override disabled means uptime stability wins — the device that has been running longer is assumed more reliable. Resetting the uptime to 0 on the current primary causes its uptime to drop below the secondary's, triggering re-election. The secondary wins because it now has the higher HA uptime, without touching priority values.
Q2 — MODEL ANSWER
With override enabled, priority always wins after monitored ports. The advantage is deterministic primary selection. The critical disadvantage: when the original primary recovers, it immediately triggers another failover to reclaim its primary role from the secondary that replaced it. This double-failover disrupts sessions twice — once when it fails, once when it returns.
SECTION 02

Primary Election Criteria

📷 images/s2-primary-election.png

Election flowchart: Override disabled vs Override enabled criteria ordering.

Flat colorful illustration: two side-by-side diamond flowcharts labeled "Override Disabled" and "Override Enabled". Each shows decision boxes in teal for: monitored ports, HA uptime/priority, priority/HA uptime, serial number. Bold outlines, pastel palette, arrow connectors, minimal text labels. Educational infographic style.

When multiple FortiGates negotiate for primary, the election evaluates criteria in a specific order, stopping at the first criterion that produces a winner. Two orderings exist depending on the override setting.

Override Disabled (default): The cluster evaluates: (1) most connected monitored ports → (2) highest HA uptime (by at least 5 minutes) → (3) highest configured priority → (4) highest serial number. HA uptime outranks priority, which means a newly rebooted device with high priority will lose to a lower-priority device that has been running longer.

Override Enabled: The order becomes: (1) monitored ports → (2) priority → (3) HA uptime → (4) serial number. Priority now decides before uptime, so the device with the highest priority always becomes primary when available. Override must be manually enabled on each member — it is not synchronized.

FortiGate CLI — Enable Override & Force Failover
# Enable override (run on each member)
config system ha
    set override enable
end

# Force failover when override is disabled
# (run on the current primary)
diagnose sys ha reset-uptime
Exam tip: Override and priority values are NOT synchronized. You must configure them individually on each cluster member. Forgetting this is a common lab mistake.
🧠
MENTAL NOTE
Override disabled order: monitored ports → HA uptime → priority → serial. Override enabled order: monitored ports → priority → HA uptime → serial. Override enabled causes double-failover when primary recovers. Override settings are NOT cluster-synchronized — set manually on each device.

💭 THINK FIRST · HEARTBEAT & SYNC

FGCP uses non-IP Ethernet frames for heartbeats — not TCP/IP — which means you can't route heartbeat traffic across Layer 3 boundaries. Understanding the distinct Ethernet types and what each carries is key to diagnosing HA issues.

  • What is the risk of running session synchronization over the same link as heartbeat traffic, and what happens if all dedicated session sync interfaces fail?
  • Why does FGCP use Ethernet types 0x8890/0x8891/0x8893 instead of IP for cluster communication?
Q1 — MODEL ANSWER
Session synchronization requires significantly more bandwidth than heartbeats — especially with many active sessions. Mixing them can starve heartbeat traffic, causing false failovers. If all dedicated session sync interfaces fail, session sync falls back to the HA heartbeat link automatically, restoring functionality at the cost of increased heartbeat link load.
Q2 — MODEL ANSWER
Using custom Ethernet types bypasses the IP routing layer, ensuring heartbeat frames stay on the local broadcast domain and cannot be accidentally routed away. It also allows FGCP to operate before any IP address assignment is configured, which is essential during early cluster formation when management IPs may not yet be set.
SECTION 03

Heartbeat & Synchronization

📷 images/s3-heartbeat-sync.png

FGCP Ethernet types: 0x8890/8891 for HA functions, 0x8893 for config sync.

Flat colorful illustration: two FortiGate boxes connected by two links labeled "Heartbeat Link" and "Session Sync Link". Above the heartbeat link, show packets labeled 0x8890 (heartbeat), 0x8891 (data sync), 0x8893 (config sync) in different colors. Bold outlines, pastel palette, minimal text. Educational infographic.

FGCP cluster communication uses proprietary Ethernet frame types rather than IP, enabling communication before IP addresses are assigned and ensuring heartbeat traffic stays local to the broadcast domain. Three Ethernet types are used:

Ethernet TypePurpose
0x8890 and 0x8891Heartbeats, device discovery, primary election, data sync, device failure detection, and traffic redistribution
0x8893Configuration synchronization

By default, session synchronization occurs over the HA heartbeat link. For better performance, configure dedicated synchronization interfaces — this separates high-bandwidth session sync traffic from heartbeat packets. If multiple session sync interfaces are configured, traffic is load balanced. If all sync interfaces fail, synchronization falls back to the heartbeat link automatically.

FortiGate CLI — Dedicated Session Sync & Sniffer
# Configure dedicated session sync interfaces
config system ha
    set session-sync-dev port5 port6
end

# Sniff heartbeat packets to verify HA communication
diagnose sniff packet any "ether proto 0x8890" 4
Exam tip: Mixing heartbeat and session sync on the same link can cause false failovers under high session volume. Always use dedicated sync interfaces in production.
🧠
MENTAL NOTE
0x8890/0x8891 = heartbeat/data sync. 0x8893 = config sync. Session sync defaults to heartbeat link — use set session-sync-dev to dedicate separate interfaces. Load balanced across multiple sync interfaces. Falls back to heartbeat link if all sync interfaces fail.

💭 THINK FIRST · VIRTUAL MAC ADDRESSES

Virtual MAC addresses are what make FortiGate HA failover transparent to the network — connected switches never need to update their ARP tables because the MAC address stays constant even after a different physical device takes over. But the mechanics of how these addresses are assigned and inherited are nuanced.

  • During a failover, the new primary adopts the same virtual MAC addresses. Why does the new primary also send gratuitous ARP packets — and when might that not be enough?
  • Why does Fortinet strongly recommend using unique HA group IDs for each cluster in the same broadcast domain?
Q1 — MODEL ANSWER
Gratuitous ARP tells switches that the virtual MAC is now reachable through a different physical port, prompting them to update their MAC forwarding tables. Some high-end switches don't process gratuitous ARPs fast enough — so the former primary's interfaces must be shut down for 1 second (link-failed-signal enable) to force the switch to clear its MAC table entries via a link-down event.
Q2 — MODEL ANSWER
The virtual MAC address is derived from the HA group ID. Two clusters in the same broadcast domain using the same group ID will generate identical virtual MAC addresses for the same interface index — causing catastrophic MAC address conflicts that corrupt forwarding tables and drop traffic from both clusters.
SECTION 04

Virtual MAC Addresses and Failover

📷 images/s4-virtual-mac.png

Primary assigns virtual MACs; secondary inherits same MACs on failover.

Flat colorful illustration: two-panel diagram. Left panel shows "Primary FortiGate" with virtual MAC badges on each port. Right panel shows "Failover" arrow and "New Primary" with same MAC badges, plus a "Gratuitous ARP" broadcast packet labeled. Pastel palette, bold outlines, no shadows.

When a primary FortiGate joins a cluster, FortiGate assigns a virtual MAC address to each interface except HA heartbeat and reserved management interfaces. The primary informs all secondary devices of these assignments. During a failover, the newly elected primary adopts the identical virtual MAC addresses — so connected switches see no MAC change and do not need to relearn paths.

After failover, the new primary broadcasts gratuitous ARP packets to inform switches that the virtual MAC is now reachable through a different port. Most switches update their MAC forwarding tables immediately. Some high-end switches may not — in those cases, enable link-failed-signal to force the former primary's interfaces to drop for one second, triggering switch MAC table clearing.

FortiGate supports three virtual MAC assignment methods (highest priority first): manual per-interface, automatic per-interface, and group-ID-based (default). The default method derives MAC addresses from the vcluster ID, group ID, and physical interface index — four different logic formulas apply depending on these values. Two clusters in the same LAN using the same group ID will generate conflicting virtual MACs.

FortiGate CLI — Link-Failed-Signal & MAC Verification
# Force link-down on failover to clear switch MAC tables
config system ha
    set link-failed-signal enable
end

# Check virtual MAC address on an interface
diagnose hardware deviceinfo nic wan1 | grep addr

# Manual virtual MAC assignment per interface
config system interface
    edit port1
        set virtual-mac <mac_address>
    next
end
Analogy

Virtual MAC failover works like a relay race baton pass — the runner changes, but the baton (the MAC) stays the same.

  • Virtual MAC address — the baton that never changes hands visibly to the audience (the network)
  • Gratuitous ARP — the announcer telling the crowd which lane the new runner is in
  • Link-failed-signal — dropping the baton briefly so the scoreboard (switch MAC table) resets

Use link-failed-signal enable for switches that don't update MAC tables on gratuitous ARP. Two clusters on same LAN must use different group IDs to avoid MAC conflicts.

💭 THINK FIRST · ACTIVE-ACTIVE LOAD BALANCING

Active-active HA is often misunderstood as simple traffic splitting. In reality, all traffic still arrives at the primary first — the primary then decides which secondary to forward sessions to. The goal is leveraging unused secondary CPU, not raw bandwidth multiplication.

  • Why does active-active mode typically show more traffic on the primary than on secondary devices, even when load balancing is configured?
  • When would you enable load-balance-all, and what traffic does it affect that isn't load balanced by default?
Q1 — MODEL ANSWER
All client and server traffic is always sent to the primary first, since only the primary has virtual MAC addresses on data interfaces. The primary then redistributes select sessions to secondaries via MAC address rewrite (encapsulated in 0x8891 frames). Return traffic from secondaries also routes back through the primary for proxy sessions, so the primary always carries more total traffic than any secondary.
Q2 — MODEL ANSWER
By default, only sessions subject to proxy inspection are distributed to secondaries. Enable load-balance-all to also distribute flow-inspected and uninspected sessions. You'd use this when you have high-throughput flow or pass-through traffic that isn't proxy-inspected but still benefits from secondary processing.
SECTION 05

Active-Active Load Balancing

📷 images/s5-active-active.png

Active-active traffic flow: primary receives all traffic, distributes sessions to secondary.

Flat colorful illustration: Client on left, Primary FortiGate in center-top, Secondary FortiGate in center-bottom, Server on right. Arrows showing all traffic arriving at primary, primary forwarding some sessions to secondary via dashed arrow (labeled 0x8891), secondary responding back through primary. Round-robin labels on sessions. Pastel palette, bold outlines.

In active-active mode, all cluster devices process traffic simultaneously. However, all incoming traffic is sent to the primary first, since only the primary holds virtual MAC addresses on data interfaces. The primary then selects sessions to distribute to secondary devices using one of six load balancing schedules.

ScheduleBehavior
round-robinDefault. Sessions distributed equally across all members.
noneLoad balancing off — primary handles all sessions.
leastconnectionSessions sent to member with fewest active sessions.
weight-round-robinHigher-weight members handle proportionally more sessions.
randomSessions randomly distributed across members.
ipSame source/destination IP pair always goes to same member.
ipportDistribution based on source/destination IP and port.

Only sessions subject to proxy inspection are distributed to secondaries by default. To load balance flow-inspected or uninspected sessions, enable load-balance-all. Note that FGCP active-active cannot load balance traffic traversing inter-VDOM links.

FortiGate CLI — Load Balancing Schedule
config system ha
    set schedule round-robin
    set load-balance-all enable
end
Note: Active-active leverages unused CPU on secondary devices. In practice, the primary always carries more traffic than secondaries because all endpoints send traffic to the primary's virtual MAC. Secondary devices only process sessions forwarded by the primary.
🧠
MENTAL NOTE
Default schedule: round-robin. Only proxy-inspected sessions distributed by default — enable load-balance-all for flow/pass-through traffic. Active-active cannot load balance inter-VDOM traffic. Primary always handles more traffic than secondaries — all endpoints talk to primary's virtual MAC first.
