Configure ADVPN

Master the hub-and-spoke IPsec configuration for ADVPN — IKEv2 settings, auto-discovery roles, overlay addressing, and multi-hub network-id assignment — essential for the NSE7 Enterprise Firewall exam.

ADVPN turns a bottleneck hub into a dynamic springboard for direct spoke-to-spoke tunnels.

Understanding the three ADVPN roles — sender, receiver, forwarder — and the IKEv2 requirement is high-frequency exam territory.

💭 THINK FIRST · ADVPN OVERVIEW

Traditional hub-and-spoke VPN routes all inter-branch traffic through a central hub — even when two spokes are geographically close. ADVPN promises to eliminate that detour, but it requires the hub to remain involved in tunnel setup even though it steps out of the data path afterward. Think about what that means for initial traffic flow.

  • In a standard hub-and-spoke VPN, what are the two main downsides when branch-to-branch traffic always traverses the hub, and how does ADVPN solve each one?
  • ADVPN supports both single-hub and multiple-hub architectures. What additional complexity does a multi-hub design introduce that a single-hub design avoids?
Q1 — MODEL ANSWER
Hub-and-spoke creates two problems: latency (traffic takes a longer round-trip path through the hub) and bottleneck (the hub becomes a throughput choke point for all inter-branch flows). ADVPN solves latency by creating a shortcut tunnel directly between spokes after the first packet travels via the hub. It solves the bottleneck by shifting subsequent data traffic off the hub once that shortcut is established.
Q2 — MODEL ANSWER
Multi-hub designs require configuring the auto-discovery-forwarder role on inter-hub tunnels so that shortcut offer/query messages can propagate across overlay boundaries. You also need network-id on IKEv2 phase 1 interfaces to distinguish which hub a particular tunnel belongs to when multiple IKEv2 tunnels exist between the same gateway pair.
SECTION 01

ADVPN — Efficient Full-Mesh Meets Simple Hub-and-Spoke

In traditional hub-and-spoke VPN topologies, all branch-to-branch traffic routes through the central hub firewall, introducing latency and creating a throughput bottleneck. Creating manual full-mesh IPsec tunnels between every branch is possible but becomes operationally expensive — every new spoke requires O(n) new tunnel configurations.

ADVPN (Auto-Discovery VPN) is Fortinet's proprietary solution that combines the operational simplicity of hub-and-spoke with the performance of full-mesh. Spoke-to-spoke IPsec tunnels are dynamically created on demand: the first packet travels via the hub, the hub signals both spokes to negotiate a direct shortcut tunnel, and subsequent traffic takes the shortcut — all without manual intervention.

ADVPN supports single or multiple-hub architectures, NAT traversal for on-demand tunnels, both IPv4 and IPv6, and dynamic routing protocols including BGP, OSPF, RIPv2, and RIPng.

Key concept: ADVPN is a Fortinet-proprietary protocol — third-party spoke gateways cannot participate in shortcut negotiation, though they can still be part of the overlay network using hub routing and phase 2 dst-subnet configuration.
🧠
MENTAL NOTE
ADVPN is Fortinet-proprietary and IKEv2 is required (IKEv1 is supported but IKEv2 is strongly preferred). The hub always participates in shortcut signaling but exits the data path once the spoke-to-spoke tunnel is up. Dynamic routing (BGP/OSPF) runs on the overlay network, not the underlay.
Analogy

ADVPN works like an airport hub that arranges direct charter flights between passengers who meet there.

  • Hub airport — the ADVPN hub FortiGate that handles the initial connection and shortcut negotiation
  • Spoke airports — branch FortiGates; passengers (traffic) first fly to the hub, then get redirected on a direct flight
  • Shortcut tunnel — the new direct charter flight between two spoke airports, bypassing the hub for future journeys
  • Overlay network — the airline reservation system shared by all airports, used to coordinate routes

💭 THINK FIRST · IKEv2 IN ADVPN

ADVPN can technically run on IKEv1 but Fortinet strongly recommends IKEv2. The difference isn't just fewer messages — IKEv2 introduces a Fortinet-proprietary field called the network-id that solves a specific ADVPN problem that IKEv1 cannot address at all.

  • IKEv2 uses only 4 total messages (2 exchanges) vs 6 for IKEv1 aggressive mode and 9 for IKEv1 main mode. Why does message count matter specifically in an ADVPN environment where tunnels are created on demand?
  • What is the network-id in IKEv2 ADVPN, and what specific multi-hub scenario problem does it solve that IKEv1 cannot?
Q1 — MODEL ANSWER
In ADVPN, spoke-to-spoke shortcut tunnels are negotiated on demand — every new spoke pair requires a fresh IKE negotiation. With IKEv1 main mode (9 messages) or aggressive mode (6 messages), the overhead per tunnel setup is significantly higher. IKEv2's 4-message negotiation reduces the time-to-first-packet for shortcut tunnels, which is critical when latency-sensitive applications (like VoIP) trigger the shortcut and must wait for it to come up.
Q2 — MODEL ANSWER
The network-id is a Fortinet-proprietary IKEv2 attribute assigned per phase 1 interface. When two FortiGates have multiple IPsec tunnels between the same local and remote IP pair (common in multi-hub designs), the network-id tells each peer which specific phase 1 to use for a given shortcut negotiation. IKEv1 has no equivalent field, so it cannot distinguish between multiple tunnels sharing the same gateway endpoints — making multi-hub ADVPN with IKEv1 unreliable or impossible.
SECTION 02

Advantages of IKEv2 in ADVPN

📷 images/s2-ikev2-comparison.png

IKEv2 uses only 4 total messages vs 6 (IKEv1 aggressive) or 9 (IKEv1 main mode), plus adds network-id support for multi-hub ADVPN.

Flat colorful illustration: three vertical swim-lanes labeled "IKEv1 Aggressive (6 msgs)", "IKEv1 Main Mode (9 msgs)", and "IKEv2 (4 msgs)". For ADVPN, IKEv2 is the preferred IKE version because it establishes security associations in just 4 messages across two exchanges (IKE_SA_INIT and IKE_AUTH), compared to IKEv1's 6 messages (aggressive) or 9 messages (main mode). In an ADVPN environment where shortcut tunnels are created on demand, this reduced negotiation overhead directly improves spoke-to-spoke connection setup time.

The network-id is a Fortinet-proprietary IKEv2 attribute. When multiple IKEv2 tunnels exist between the same local/remote gateway pair (common in multi-hub ADVPN deployments), the network-id lets IPsec peers select the correct phase 1. Without it, FortiGate cannot distinguish which hub a shortcut message belongs to when two hubs share the same underlay gateway.

Exam tip: In IKEv1 aggressive mode, peer IDs are transmitted in clear text — a security risk. IKEv1 main mode encrypts peer IDs but uses 9 messages. IKEv2 encrypts peer IDs AND uses only 4 messages. The network-id field is IKEv2-only and required for multi-hub ADVPN.
🧠
MENTAL NOTE
IKEv2 = 4 messages, encrypted peer IDs, network-id support, AES-GCM/ECDH. IKEv1 aggressive = 6 messages, clear-text peer IDs, no network-id. The network-id is mandatory when two hubs have tunnels to the same spoke — it selects the right phase 1. Always set ike-version 2 for ADVPN.

💭 THINK FIRST · HUB & SPOKE CONFIG

ADVPN configuration has three distinct roles that must be applied to the correct phase 1 interface on each device. Getting the sender vs. receiver direction wrong is the most common configuration mistake. The auto-discovery-forwarder role only appears in multi-hub designs.

  • The hub is configured with auto-discovery-sender and the spoke is configured with auto-discovery-receiver. Why does the hub "send" and the spoke "receive" — what is actually being sent and received?
  • Why must add-route be disabled on the hub and net-device also disabled? What breaks if either is left enabled?
Q1 — MODEL ANSWER
The hub "sends" shortcut offer messages to the initiating spoke (Spoke 1) when it detects inter-spoke traffic passing through. The spoke "receives" those shortcut offers and responds by querying the hub for the target spoke's WAN IP. So auto-discovery-sender means "this interface will send ADVPN shortcut messages" and auto-discovery-receiver means "this interface will accept ADVPN shortcut messages and initiate the negotiation process."
Q2 — MODEL ANSWER
add-route must be disabled on the hub because dynamic routing (BGP/OSPF) is responsible for learning the protected subnets behind spokes — if add-route is enabled, FortiGate creates static IKE routes that conflict with the dynamic routing entries. net-device must be disabled to prevent FortiGate from creating a separate dynamic interface per spoke, which would break the single-interface model needed for ADVPN shortcut signaling.
SECTION 03

Hub & Spoke IPsec Configuration

📷 images/s3-hub-spoke-config.png

Hub phase 1: set type dynamic, ike-version 2, add-route disable, net-device disable, auto-discovery-sender enable. Spoke phase 1: ike-version 2, auto-discovery-receiver enable, net-device enable.

Flat colorful illustration: two side-by-side CLI terminal boxes. Left box labeled "Hub FortiGate" shows key config lines highlighted in red: ike-version 2, add-route disable, auto-discovery-sender enable. Right box labeled "Spoke FortiGate" shows: ike-version 2, auto-discovery-receiver enable, net-device enable. Arrows between them labeled "Shortcut Offer" and "Shortcut Accept". Pastel palette, bold outlines, no shadows.

ADVPN phase 1 configuration uses three distinct role settings that must be applied on the correct device and tunnel interface:

  • auto-discovery-sender enable — configured on the hub's spoke-facing phase 1 interface. When IPsec traffic transits the hub, it sends a shortcut offer to the originating spoke.
  • auto-discovery-receiver enable — configured on the spoke's hub-facing phase 1 interface. Enables the spoke to receive shortcut offers and initiate direct tunnel negotiation.
  • auto-discovery-forwarder enable — configured on inter-hub tunnels in multi-hub deployments. Forwards shortcut messages across overlay network boundaries.
FortiGate CLI — Hub Phase 1
config vpn ipsec phase1-interface
    edit "VPN1"
        set type dynamic
        set interface "port1"
        set ike-version 2
        set net-device disable
        set add-route disable
        set auto-discovery-sender enable
    next
end
FortiGate CLI — Spoke Phase 1
config vpn ipsec phase1-interface
    edit "Hub1-VPN1"
        set ike-version 2
        set auto-discovery-receiver enable
        set net-device enable
    next
end

config vpn ipsec phase2-interface
    edit "Hub1-VPN1"
        set phasename "Hub1-VPN1"
        set proposal aes256-sha256
    next
end

For phase 2 on the hub, quick modes must be set to all (0.0.0.0/0.0.0.0) so the hub can accept any spoke subnet. Firewall policies must permit traffic from spokes to hub, hub to spokes, and between spokes (transiting through the hub before shortcut establishment).

Exam tip: On the hub, set add-route disable (dynamic routing handles subnet learning) and net-device disable (prevents per-spoke dynamic interfaces). On spokes, net-device should be enabled. Phase 2 on the hub must use src/dst 0.0.0.0/0 to accept all spoke subnets.
🧠
MENTAL NOTE
Hub = sender + add-route disable + net-device disable + type dynamic. Spoke = receiver + net-device enable. Multi-hub adds forwarder on inter-hub tunnels + network-id to distinguish tunnels. Phase 2 hub selector must be 0.0.0.0/0.0.0.0 for all spokes.

💭 THINK FIRST · OVERLAY & INTERFACES

ADVPN has two distinct network layers that serve completely different purposes. IPsec tunnels are built over underlay IP addresses (real internet IPs), but dynamic routing protocols run over overlay IP addresses assigned to the IPsec virtual interfaces. Confusing these two layers is a common ADVPN troubleshooting trap.

  • Why can't the dynamic routing protocol run on the underlay (real internet) IP addresses? What specifically breaks if you try to peer BGP over underlay IPs in an ADVPN topology?
  • In the example topology, Spoke 1's next-hop to reach Spoke 2's subnet is the overlay IP 172.16.1.3 (Spoke 2's IPsec interface), not Spoke 2's underlay IP 100.65.3.113. Why?
Q1 — MODEL ANSWER
Dynamic routing must run on overlay IPs because the routing protocol needs to advertise local subnets and receive routes from all overlay peers within the same logical network. Underlay IPs are internet-facing and belong to different ISP subnets — you can't form a BGP neighbor-range across arbitrary internet addresses without complex static peering. The overlay creates a unified /24 (e.g. 172.16.1.0/24) that all hub and spokes share, enabling BGP neighbor-range configuration and route-reflector client setup.
Q2 — MODEL ANSWER
The next-hop is Spoke 2's overlay IPsec interface IP (172.16.1.3) because that is the address used by the routing protocol (BGP) to advertise Spoke 2's local subnet. The IPsec virtual interface is automatically created when the phase 1 interface is configured, and it's this overlay address — not the underlay WAN IP — that appears in the routing table as the BGP next-hop after the shortcut tunnel is established.
SECTION 04

Overlay Network & IPsec Interface Addressing

📷 images/s4-overlay-network.png

IPsec tunnels use underlay (internet) IPs; BGP routing peers use overlay IPs on the virtual IPsec interfaces (172.16.1.0/24). The next-hop after shortcut is the spoke's overlay IP.

Flat colorful illustration: a hub node connected to two spoke nodes. Two colored layers shown: a lower "Underlay" layer with ISP IP addresses (100.65.x.x) on each device, and an upper "Overlay" layer with private IP addresses (172.16.1.x) on the IPsec virtual interfaces. Arrows between spokes labeled "Shortcut Tunnel (underlay)" and "BGP routing (overlay)". Pastel palette, bold outlines, no shadows, educational feel.

ADVPN relies on two distinct network layers that serve different purposes. IPsec tunnels are established over underlay IP addresses — the real internet or WAN addresses assigned to physical interfaces (e.g., 100.65.0.101/24 on the hub). Dynamic routing protocols (BGP, OSPF) run over the overlay network, which is a private address space assigned to the IPsec virtual interfaces.

Each hub and spoke receives an IP address on the shared overlay network (e.g., 172.16.1.0/24). The hub is assigned a broadcast address (172.16.1.1 with remote-ip 172.16.1.254/24) while each spoke gets a unique /32 address in the same range. This allows all devices to participate in the routing protocol and dynamically share their local network information.

FortiGate CLI — Hub IPsec Interface (Overlay)
config system interface
    edit "VPN1"
        set ip 172.16.1.1 255.255.255.255
        set remote-ip 172.16.1.254/24
    next
end
FortiGate CLI — Spoke1 IPsec Interface (Overlay)
config system interface
    edit "Hub1-VPN1"
        set ip 172.16.1.2 255.255.255.255
        set remote-ip 172.16.1.1/24
    next
end

After the shortcut tunnel is established between Spoke 1 and Spoke 2, the routing table shows the next-hop as the overlay IP of Spoke 2 (e.g., 172.16.1.3), even though the actual IPsec tunnel is built over underlay IP 100.65.3.113. Phase 1 interface, phase 2 interface, and IPsec virtual interface are three distinct concepts — each phase 1 interface has exactly one IP address from the overlay network.

Note: The overlay network is essential for dynamic routing to work. Without it, firewalls cannot advertise local networks within the hub-and-spoke topology. Each internet connection requires a separate phase 1 interface and therefore a separate overlay IP address.
🧠
MENTAL NOTE
Underlay = real internet IPs on physical interfaces (IPsec tunnel endpoints). Overlay = private IPs on IPsec virtual interfaces (routing protocol peer addresses). BGP next-hop after shortcut = overlay IP of destination spoke, not its underlay WAN IP. Hub remote-ip uses /24 broadcast; spokes use /32 with remote-ip pointing to hub's overlay IP.

💭 THINK FIRST · NON-ADVPN SPOKES

Real-world networks often have a mix of FortiGate and third-party VPN gateways. ADVPN shortcuts are Fortinet-proprietary, so third-party spokes will never receive or send shortcut messages. But they can still join the overlay routing table — the question is how the hub learns their subnets and distributes return routes.

  • A non-ADVPN spoke needs to participate in overlay routing so the hub can forward traffic to it. What two phase 2 configuration elements allow this without enabling ADVPN shortcuts?
  • Why does the additional phase 2 entry for the overlay advertisement need to be named alphabetically before the main phase 2 entry? What breaks if it comes second?
Q1 — MODEL ANSWER
Two elements: (1) add-route enable in the additional phase 2 entry — this tells FortiGate to install IKE routes for the overlay subnet, allowing the hub to learn the non-ADVPN spoke's overlay segment via the IPsec SA negotiation. (2) dst-subnet set to the overlay network range (e.g. 172.16.1.0/24) — this is the "Overlay_advertisement" phase 2 that covers all spoke overlay IPs and enables the hub to inject a return route for the non-ADVPN spoke's subnets into the dynamic routing protocol.
Q2 — MODEL ANSWER
Phase 2 lookup occurs in alphabetical order. The specific overlay advertisement phase 2 (with a narrower dst-subnet) must be matched first before the broader catch-all phase 2 (0.0.0.0/0). If the names are reversed alphabetically, the catch-all "Spoke" entry matches first, the overlay subnet gets treated as a normal data tunnel, and the add-route/dst-subnet mechanism that enables hub routing for the non-ADVPN spoke never triggers.

Non-ADVPN Spokes & Mixed Vendor Integration

📷 images/s5-non-advpn-spokes.png

Use Case 4: Spoke 1 (FortiGate, ADVPN-capable) gets shortcuts. Spoke 2 (third-party) uses Overlay_advertisement phase 2 with add-route enable + dst-subnet for overlay participation without shortcuts.

Flat colorful illustration: a hub connected to two spokes. Left spoke (Spoke 1) has a FortiGate logo and shows green shortcut arrows to the hub and a label "ADVPN Shortcuts: YES". Right spoke (Spoke 2) has a generic router icon and shows a label "ADVPN Shortcuts: NO". A text box near Spoke 2 shows "Overlay_advertisement phase2 / add-route enable / dst-subnet 172.16.1.0/24". Pastel palette, bold outlines, no shadows.

ADVPN is a Fortinet-proprietary protocol. When a spoke is a third-party IPsec gateway, it cannot participate in shortcut negotiation — it will never send or receive ADVPN offer/query/reply messages. However, a third-party spoke can still participate in the ADVPN hub-and-spoke architecture for routing purposes.

For a non-ADVPN spoke to share its subnets via dynamic routing, it must announce its networks using an IP address from the overlay network segment. The hub phase 2 for these spokes requires a special configuration with two entries:

FortiGate CLI — Hub Phase 2 for Mixed (Non-ADVPN Spoke)
config vpn ipsec phase2-interface
    edit "Overlay_advertisement"
        set phasename "Spoke"
        set proposal aes256-sha256
        set add-route enable
        set dst-subnet 172.16.1.0 255.255.255.0
    next
    edit "Spoke"
        set phasename "Spoke"
        set proposal aes256-sha256
    next
end

The Overlay_advertisement phase 2 entry must be named so it alphabetically precedes the regular phase 2 entry (Spoke). Phase 2 lookup occurs in alphabetical order — the specific overlay advertisement must match first, before the catch-all 0.0.0.0/0 phase 2. The diag vpn ike config list command shows the phase 2 entries in lookup order to verify correct naming.

Exam tip: The Overlay_advertisement phase 2 name MUST come before the regular phase 2 name alphabetically (O before S). Phase 2 lookup is alphabetical — if the catch-all matches first, the overlay subnet advertisement breaks. Use diag vpn ike config list to verify order.
🧠
MENTAL NOTE
Non-ADVPN spokes: no shortcuts, but can participate in overlay routing. Requires two phase 2 entries on hub: (1) "Overlay_advertisement" with add-route enable + dst-subnet = overlay subnet — must come FIRST alphabetically. (2) Regular "Spoke" entry for data traffic. Phase 2 lookup is alphabetical — order matters.
