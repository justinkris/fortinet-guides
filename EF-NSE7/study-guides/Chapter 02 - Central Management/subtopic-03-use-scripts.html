Use Scripts on FortiManager

Script execution contexts, ZTP and LTP, pre-run and CLI templates, and language options — automating FortiGate configuration at scale without touching the GUI.

Where a script runs determines what it changes — and whether you need an extra install step to make it stick.

The exam tests execution context side effects: which target gets modified, what sync is triggered, and when you must manually install afterwards.

💭 THINK FIRST · EXECUTION CONTEXTS

FortiManager scripts can run in four distinct locations: directly on FortiGate, on the device database, on a policy package, or on the global database. Each context affects a different target and has different implications for synchronization and subsequent install steps.

  • If you run a script on the device database and it modifies configuration, what is the resulting sync state — and what must you do next to push those changes to FortiGate?
  • Why does running a script directly on FortiGate (Remote FGT) trigger an auto-retrieve, but changes to firewall policies still require manual intervention?
Q1 — MODEL ANSWER
Running a script on the device database changes the device layer configuration without pushing anything to FortiGate. The Config Status for that device changes to Modified. To complete the change, you must then install device settings (or a policy package if policy changes are also required) to push the modified device database to the actual firewall.
Q2 — MODEL ANSWER
When a script runs directly on FortiGate via Remote FGT, FortiManager detects the change and triggers an auto-retrieve to sync the device database — this works for device settings. However, if the script modifies firewall policy settings, those changes live in the policy layer, not the device layer. Auto-retrieve can't automatically import policy changes; an explicit Import operation is needed first, and then a policy package install to reconcile the policy layer.

Four execution contexts — each targets a different layer and requires different follow-up steps to propagate changes to the actual FortiGate.

FortiManager scripts can be written in CLI or Tcl and executed in one of four contexts:

  • Remote FortiGate Directly (via CLI): Runs the script directly on FortiGate through the FGFM tunnel. For non-policy changes, FortiManager auto-retrieves the device database — Config Status shows Synchronized. For policy changes, auto-retrieve cannot sync the policy layer automatically; a manual Import and then policy package install are required.
  • Device Database: Script modifies the device layer database on FortiManager only — nothing is pushed to FortiGate. Config Status changes to Modified. To complete the change, install device settings or a policy package.
  • Policy Package (or ADOM Database): Script modifies the policy layer — creates or changes firewall objects and policies within the selected policy package. The policy package is flagged as Modified. Changes reach FortiGate only after installing the policy package.
  • Global Database: Script runs against the global ADOM's database. Changes to global policies require manual action (assign or auto-install) to propagate to local ADOMs and then to FortiGate.
Critical sync rule: Running a script on the device database does not push changes to FortiGate — it only marks the device as Modified. Running on policy package does not update the device database or FortiGate — it marks the package as Modified. Always check the resulting Config Status and complete the install step.
🧠
MENTAL NOTE
Remote FGT = runs on firewall directly; auto-retrieve syncs device DB (not policy layer). Device DB = modifies device layer only → install to push. Policy Package = modifies policy layer → install policy package to push. Global DB = modifies global policies → assign or auto-install to propagate.
Analogy

Script execution contexts work like filing a document in different offices — where you file it determines who receives it and what approval step comes next.

  • Remote FGT (the actual store) — you hand the memo directly to the store manager; the corporate filing system gets a copy automatically (auto-retrieve), but anything involving the company policy manual still needs a separate import process
  • Device Database (regional records office) — you update the regional filing cabinet; the store doesn't know yet until the regional office sends the memo (install device settings)
  • Policy Package (corporate policy manual) — you update the policy manual at HQ; no store gets it until HQ formally distributes the updated manual (install policy package)
  • Global Database (corporate HQ archive) — you file in the master archive; regional offices don't get it until HQ assigns or auto-installs the update to each region

💭 THINK FIRST · ZTP AND LTP

Large enterprises deploy hundreds of FortiGate devices to remote sites — it's not practical to have IT staff manually configure each one on-site. Zero-touch provisioning (ZTP) and low-touch provisioning (LTP) solve this by having FortiManager pre-configure a model device before the real hardware even arrives.

  • What is the difference between ZTP and LTP in terms of how the FortiGate discovers and connects to FortiManager?
  • What is a model device, and what role does it play in the ZTP/LTP workflow?
Q1 — MODEL ANSWER
ZTP: FortiGate automatically connects to the WAN/internet and links to FortiManager without any preconfiguration — the device discovers FortiManager on its own. LTP: some initial setup is required on FortiGate (specifying network settings and the FortiManager IP/address) before the device can discover and connect. ZTP is truly zero-touch on the FortiGate side; LTP requires minimal initial configuration.
Q2 — MODEL ANSWER
A model device is a placeholder FortiGate entry created in FortiManager before the physical hardware connects. The admin pre-configures settings and policies on the model device. When the real FortiGate connects and auto-links, FortiManager pushes the model device's settings to it via Quick Install and then replaces the model device entry with the real device for ongoing central management.

ZTP and LTP use a model device as a configuration template — when the real FortiGate connects, FortiManager pushes settings and replaces the model entry with the real device.

Zero-touch provisioning (ZTP) and low-touch provisioning (LTP) automate the onboarding of FortiGate devices — particularly useful for large deployments or remote sites where having IT staff manually configure each device is impractical.

The workflow uses model devices: placeholder FortiGate entries added to FortiManager before the physical hardware arrives. The admin configures the model device using a serial number or pre-shared key, assigns provisioning templates, policy packages, and other settings. When a new FortiGate connects and establishes an FGFM tunnel:

  1. FortiManager runs the auto-link process, matching the real FortiGate to its model device entry.
  2. Settings and policies from the model device are pushed to the FortiGate via Quick Install.
  3. The real FortiGate replaces the model device in FortiManager for ongoing central management.

The difference between ZTP and LTP is how the FortiGate finds FortiManager:

  • ZTP: FortiGate automatically connects to FortiManager via the WAN or internet with no preconfiguration on the device.
  • LTP: Requires minimal initial setup on FortiGate — specifying network settings and the FortiManager IP — before the device can discover and connect.

Besides FortiManager, other ZTP methods include FortiSOAR with FortiManager, Ansible, Terraform, custom API calls, FortiProvision, FortiZTP, and FortiDeploy. The best method depends on expertise, budget, ability to preconfigure FortiGate, and deployment scale.

Auto-link behavior: When "Automatically Link to Real Device" is enabled, FortiManager applies configurations immediately when the FGFM tunnel is established. When disabled, you must manually push configuration changes after the tunnel is active.

ZTP = FortiGate auto-discovers FortiManager, zero preconfiguration. LTP = minimal initial setup required on FortiGate. Both use a model device: pre-configured placeholder → auto-link → real device replaces model. Provisioning pushes via Quick Install.

💭 THINK FIRST · CLI TEMPLATES

FortiManager provides two types of CLI-based templates: pre-run CLI templates that fire once during device onboarding and then disappear, and CLI templates that stay assigned and continuously override the device layer. Both can use metadata variables for dynamic configuration.

  • What is the key behavioral difference between a pre-run CLI template and a regular CLI template?
  • Why do CLI templates "overwrite" the device database — and what does that mean for any settings you had configured there before assigning the template?
Q1 — MODEL ANSWER
Pre-run CLI templates are for one-time tasks during ZTP/LTP onboarding — they are automatically unassigned (auto-detached) from the FortiGate device database after the Quick Install process completes, so they don't remain in the device database. Regular CLI templates are persistent — they remain assigned to the device and are continuously applied, overwriting the device database each time device settings are installed.
Q2 — MODEL ANSWER
CLI templates are provisioning templates, which means they have precedence over other device layer settings. When you assign a CLI template to a device, it overwrites the corresponding settings in the device database — even if those values were explicitly configured there. In practice this means any device layer configuration that overlaps with a CLI template's scope will be replaced on the next install. You must treat the CLI template as the authoritative source for those settings.

Pre-run CLI templates are one-time onboarding scripts (auto-detach after Quick Install); regular CLI templates persist and continuously override the device database when installed.

Pre-run CLI templates are designed for one-time configuration tasks during ZTP and LTP device onboarding. The workflow:

  1. A FortiManager admin creates or assigns a pre-run CLI template to a new FortiGate added as a model device.
  2. The admin uses Quick Install to deploy configurations from the pre-run CLI template directly to the FortiGate device database.
  3. FortiManager automatically unassigns (auto-detaches) the pre-run CLI template from the device database after Quick Install completes.
  4. When the new FortiGate connects and "Automatically Link to Real Device" is enabled, FortiManager applies configurations automatically. If disabled, you must manually push after the FGFM tunnel is active.

CLI templates (regular) are persistent provisioning templates designed for repeated use. Unlike pre-run templates, they remain assigned to the device after the initial setup and are not automatically unassigned. Key characteristics:

  • CLI templates are provisioning templates — they overwrite the device database on assignment and on every subsequent install.
  • Configuration changes via CLI template do not require modifying policy layer settings; they apply via Install Device Settings or Quick Install.
  • Both CLI templates and pre-run CLI templates support metadata variables ($ prefix) for dynamic field injection and support CLI and Jinja scripting.
FortiManager CLI — Create a CLI Template Script (example)
config firewall address
    edit "DMZ_Address"
        set subnet $DMZ_LAN_Address
    next
end
Template precedence warning: Assigning a CLI template marks the device as Modified immediately. The provisioning template status and device layer status are both flagged — this signals that changes need to be pushed to synchronize the firewall, device database, policy package, and template statuses.
🧠
MENTAL NOTE
Pre-run CLI template: one-time, auto-detaches after Quick Install. CLI template: persistent, overwrites device DB, stays assigned. Both support metadata variables ($) and CLI/Jinja scripting. Assigning either flags the device as Modified — install to apply.

💭 THINK FIRST · SCRIPT LANGUAGES

FortiManager supports five scripting approaches — CLI scripts, CLI templates, Tcl scripts, Jinja templates, and API scripting. Each has different capabilities around dynamic variables and complexity. Knowing which to choose depends on what you're trying to automate and what language expertise you have.

  • Which scripting approaches support dynamic variables, and which do not?
  • When would you choose API scripting over CLI scripts, and what is the main tradeoff?
Q1 — MODEL ANSWER
CLI templates, Tcl scripts, Jinja templates, and API scripting all support dynamic variables (metadata variables for CLI templates and Jinja; native variable syntax for Tcl and API). Plain CLI scripts do not support dynamic variables — they are static FortiOS CLI commands. This is often why CLI templates are preferred over CLI scripts for provisioning: the template version can inject per-device values via metadata variables.
Q2 — MODEL ANSWER
API scripting is best when you need to interface software applications directly with FortiManager — for example, integrating FortiManager into a CI/CD pipeline, ITSM system, or orchestration platform. The tradeoff is high complexity: API scripting requires JSON knowledge and familiarity with FortiManager's API schema, plus tools like Postman, Terraform, Insomnia, or Swagger UI. CLI scripts are simpler and leverage existing FortiOS knowledge but lack the integration depth of API calls.

Five scripting approaches — dynamic variable support and complexity determine the best fit; CLI scripts are simplest but static; API scripting is most powerful but most complex.

TypeLanguageDynamic VariablesComplexityPrimary Use
CLI Scripts FortiOS No Varies Interact directly with FortiOS — device settings, one-off changes

Tcl Scripts Tcl Yes (native Tcl) Moderate Automation tasks; software examples: Tclsh, Tkinter, ActiveTcl

If you have solid FortiGate and FortiOS knowledge, CLI scripts and CLI templates are the natural starting point — they use the same syntax you already know. If you have programming skills in Tcl or Python, Tcl and Jinja scripts allow more powerful automation with native variable support. API scripting is the choice for deep software integration — connecting FortiManager to CI/CD pipelines, ITSM systems, or orchestration platforms — at the cost of higher complexity.

Practical guidance: For most exam scenarios, focus on understanding when to use Remote FGT vs. Device DB vs. Policy Package execution contexts, and what sync state each produces. Script language selection is secondary knowledge — the context and sync behavior are what drive scenario questions.

CLI scripts: static, FortiOS syntax, no dynamic vars. CLI templates: FortiOS + metadata vars, provisioning. Tcl: moderate, native vars, automation. Jinja: Python-based, metadata vars, config schema. API: JSON, full dynamic, high complexity, software integration. Only CLI scripts lack dynamic variable support.
