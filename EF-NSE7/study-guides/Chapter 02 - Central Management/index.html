Chapter Overview

FortiManager Architecture

Managing dozens of FortiGate devices individually — each with its own policy set, firmware version, and configuration — is unsustainable at enterprise scale. FortiManager solves this with a single pane of glass: a centralized management platform where one administrator can push policies, retrieve configurations, and track revision history across every managed device. It structures everything using Administrative Domains (ADOMs), which are virtual instances that isolate groups of devices. Each ADOM maintains two internal databases: the device layer for per-device settings (network, VPN, system), and the policy layer for firewall policies and shared objects.

Above all local ADOMs sits the Global ADOM, which holds a global database of objects and policies prefixed with "g" — reserved to prevent naming conflicts. A global ADOM at version 7.6 is compatible with local ADOMs at 7.6, 7.4, and 7.2. Key operations connect FortiManager to FortiGate: Retrieve captures the current firewall config as a new revision; Auto-retrieve fires automatically when a device is added; Install device settings pushes the device layer to FortiGate with a preview; Quick install does the same without a preview, ideal for zero-touch provisioning.

Dynamic Objects & Per-Device Mapping

A central management challenge: two FortiGate devices at different branch offices may use different physical interfaces for the same logical role. Normalized interfaces solve this by creating abstract interface names on FortiManager — like LAN or WAN — that map to the correct physical port on each device. Mapping can be per-platform (same port across all devices of the same model) or per-device (individual mapping per firewall). Interface names are case-sensitive on FortiManager — LAN and lan are treated as different objects.

Beyond interfaces, dynamic object configurations extend per-device mapping to firewall addresses, user/authentication objects, and metadata variables. For example, the same address object named LAN can resolve to 172.16.0.0/24 at Branch1 and 192.168.0.0/24 at Branch2. Not all objects support per-device mapping — security profiles (web filter, antivirus, etc.) do not, so if different settings are needed per device, unique profile names are required. Metadata variables act as placeholders (indicated by a magnifying glass with $ in the GUI) that resolve to per-device values at install time.

Key mental model: Think of per-device mapping as a mail merge — the policy is the template, and each FortiGate device gets the template filled in with its own specific values at deployment time. The policy stays one object; the resolved value is different per recipient.

Scripts, Automation & Deployment

When you need to create dozens of objects, run repetitive CLI commands, or make changes that the GUI doesn't expose cleanly, FortiManager scripts are the answer. Scripts can be written in CLI (standard FortiOS commands) or Tcl and can be run against three targets: directly on a FortiGate device, against the device database, or against a policy package. Running against the device layer or policy layer keeps FortiManager in sync without bypassing its management model.

Policy deployment is a deliberate multi-step workflow, not an instant push. Install policy package transfers the policy layer to both the device layer and FortiGate, providing a wizard and installation preview with a cancel option. Reinstall policy bypasses the wizard when devices are already selected, offering a preview but applying policy package settings and any modifications directly. The global ADOM distributes policies to local ADOMs via two methods: Automatically Install (direct, no preview) or Assign (marks the ADOM as modified, requiring a manual install step). Both methods ensure that the same global policy can reach every ADOM in the organization.
