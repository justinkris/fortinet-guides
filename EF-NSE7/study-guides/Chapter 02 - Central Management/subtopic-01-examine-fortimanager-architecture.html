Study Guide · EF-NSE7

Examine FortiManager Architecture

ADOMs, device and policy layers, configuration operations, and global provisioning — the structural backbone of every enterprise FortiManager deployment.

Every FortiGate change flows through two layers — understanding which layer to use prevents policy drift and silent data loss.

The exam tests both conceptual knowledge (ADOM structure, global DB compatibility) and operational judgment (retrieve vs. import, quick install vs. reinstall policy).

💭 THINK FIRST · CORE FUNCTIONS

FortiManager organizes managed devices into virtual containers that each carry their own policy sets, provisioning templates, and manager modules. Before reading, consider why an enterprise would need multiple separate containers rather than one flat device list.

  • What is the purpose of an ADOM, and what two databases does every ADOM contain?
  • Why does the global ADOM exist as a separate special container, and what is the significance of the "g" prefix?
  • A company has 20 FortiGates across three business units, all added to the default root ADOM. An admin in Business Unit A installs a policy package. What two serious risks does this create?
Q1 — MODEL ANSWER
An ADOM (Administrative Domain) is a virtual partition on FortiManager that isolates device management for a group of FortiGate devices. Every ADOM contains two databases: the device layer (device-specific settings and revision history per FortiGate) and the policy layer (centrally managed firewall objects and policy packages). Even with ADOMs disabled, you still operate inside the default ADOM named "root."
Q2 — MODEL ANSWER
The global ADOM provides a single source of truth for policies and objects that must be identical across multiple local ADOMs. It distributes global policies downward into per-ADOM policy packages. Objects in the global ADOM use the reserved prefix "g" (e.g., g.none, g.wildcard.google.com) — you cannot create custom objects with this prefix, preventing naming collisions between global and local objects.
Q3 — MODEL ANSWER
Risk 1 — no blast radius control: a policy package install in the shared ADOM can target all 20 FortiGates, allowing one admin's action to overwrite policies on devices in other business units. Risk 2 — no administrative delegation: there is no way to scope an admin to only their own devices, so any admin can see and modify every device. ADOMs solve both problems simultaneously, along with firmware version isolation.
SECTION 01

FortiManager Core Functions

FortiManager architecture — each ADOM contains a device layer and policy layer; the global ADOM distributes shared policies to all local ADOMs.

FortiManager is Fortinet's centralized network management solution. It lets administrators manage multiple FortiGate firewalls from a single interface, centralizing policy creation, firmware management, device provisioning, and optional FortiAnalyzer log capability.

The primary organizational unit is the ADOM (Administrative Domain) — a virtual partition that isolates management of a group of FortiGate devices. When ADOMs are disabled, FortiManager still operates through a default ADOM named root. Each ADOM contains two core databases: the device layer (per-device settings and revision history) and the policy layer (centrally managed firewall objects and policy packages).

Each ADOM also includes its own set of functions: scripts (CLI and Tcl), provisioning templates, SD-WAN Manager, VPN Manager, AP Manager, FortiSwitch Manager, Extender Manager, Fabric View, and FortiAnalyzer capability. The FortiGuard database serves all ADOMs simultaneously, providing threat intelligence and firmware metadata.

A special Global ADOM sits above all regular ADOMs. It stores objects and policies prefixed with the reserved letter g and distributes identical global policies downward to multiple local ADOMs. Global-to-local compatibility spans the same version and two versions earlier: a global ADOM at 7.6 supports local ADOMs at 7.6, 7.4, and 7.2.

Key fact: The prefix g is reserved system-wide — you cannot create custom objects using this prefix. This prevents naming collisions between global and local ADOM objects.
Common misconception: "Disabling ADOMs means there is no ADOM structure." Wrong — you are always working inside an ADOM. With ADOMs disabled, that ADOM is named root, and it still contains a full device layer + policy layer + FortiGuard. The difference is that every managed device shares it with zero separation.
🧠
MENTAL NOTE
Every ADOM = device layer + policy layer. Global ADOM supports same version ± 2 (e.g., 7.6 global supports 7.4 and 7.2 locals). "g" prefix is reserved — custom objects cannot use it. FortiGuard serves all ADOMs globally.
Analogy

FortiManager's ADOM structure works like a franchise restaurant chain — corporate HQ sets the brand standards, and regional offices manage their own kitchens independently.

  • Corporate HQ (Global ADOM) — defines the core menu (global policies) every location must follow; changes propagate downward to all regions automatically
  • Regional Office (ADOM) — manages its own group of restaurants (FortiGates), applying both corporate-mandated and local policies
  • Back-of-house records (Device Layer) — each restaurant's own equipment config and service history, tracked per location
  • Recipe book (Policy Layer) — the policy packages defining what each kitchen serves; changes only go live after management approval and an explicit install step
  • Supplier network (FortiGuard) — delivers fresh ingredients (signatures, updates) to every region simultaneously

💭 THINK FIRST · DEVICE & POLICY LAYERS

FortiManager splits configuration into two layers, but changes to each behave very differently. One updates FortiGate directly when installed; the other only applies after an explicit policy deployment approval.

  • Why is it not recommended to configure firewall policies in the device layer, even though it is technically possible?
  • What is the revision history, and which layer tracks it per device?
  • A colleague edits a firewall address object in the Policy & Objects section of FortiManager. Ten minutes later, the FortiGate still shows the old value. Is this a bug, and what needs to happen next?
Q1 — MODEL ANSWER
Policies configured in the device layer are not part of a policy package and can't be centrally versioned or deployed consistently across devices. More critically, policy layer assignments overwrite the selected revision history ID in the device database — so the next time a policy package is installed, it silently overwrites any policies you wrote in the device layer. You lose that work with no warning.
Q2 — MODEL ANSWER
The revision history is a per-device log of every configuration snapshot saved in the device layer. Each FortiGate has its own revision counter that increments on every retrieve, auto-retrieve, or install operation. The device layer stores and tracks this history — not the policy layer.
Q3 — MODEL ANSWER
Not a bug. Policy layer changes never push to FortiGate automatically — even if the changed object is referenced in an active firewall policy. The edit lives only in FortiManager's database until an admin explicitly runs Install Policy Package (or Reinstall Policy). The install step is always required.

Device Layer and Policy Layer

Device layer changes install directly to FortiGate; policy layer changes require an explicit install or reinstall operation before reaching the firewall.

The device layer stores per-device settings and tracks each FortiGate's revision history. Administrators use it to configure device-specific settings: Network interfaces, VPN settings, System configuration, and Log & Report options. Changes installed from the device layer take direct effect on FortiGate. Each FortiGate added to FortiManager gets its own device database, and every retrieve, auto-retrieve, or install operation creates a new revision entry.

The policy layer is where all firewall policy objects are configured centrally — addresses, services, schedules, VIPs, security profiles, policy packages, and more. It is organized into: Policy, Policy Block, Normalized Interfaces, Firewall Objects, Security Profiles, User & Authentication, Security Fabric, and Advanced sections.

A critical distinction: changes in the policy layer take effect only after policy deployment and installation approval. The policy layer assignment overwrites the selected revision history ID in the device database. Even though you can configure policies in the device layer, the next policy package install will overwrite those settings — best practice is to restrict device layer use to device-specific (non-policy) settings only.

Gotcha: Device layer changes affect FortiGate directly when installed. Policy layer changes are deferred — they only apply after policy package install or reinstall. Never configure firewall policies in the device layer; the next policy install will silently overwrite them.
⚑ NSE7 exam trap: A policy layer change does not push automatically, even if the changed object is referenced in an active firewall policy. The install step is always required. Think of the policy layer as a Word document on a shared drive — your edits are saved, but the printer (FortiGate) never sees them until you hit print.
🧠
MENTAL NOTE
Device layer = device settings + revision history; changes push directly to FortiGate. Policy layer = policy packages + firewall objects; changes are deferred — require install or reinstall. Configure policies only in the policy layer.

💭 THINK FIRST · CONFIG OPERATIONS

FortiManager provides eight distinct operations for synchronizing configuration between the device layer, policy layer, and FortiGate. Each moves data in a specific direction and has specific side effects on revision history and policy package status. Choosing the wrong one can cause unexpected sync state changes in production.

  • What is the key difference between Retrieve and Auto-retrieve — and why does neither update the policy package?
  • When would you choose Quick Install over Install Device Settings, and what is the tradeoff?
  • A junior engineer wants to push updated firewall policies to 10 branch FortiGates. They choose Quick Install because it sounds fast. What exactly will Quick Install do, and what will it NOT do?
  • An engineer runs Auto-Retrieve on a FortiGate. Does this update the policy package in FortiManager? What exactly does it update?
Q1 — MODEL ANSWER
Retrieve is manually triggered and captures the current FortiGate config as a new revision. Auto-retrieve fires automatically whenever a FortiGate is added to the device layer. Both are strictly read operations (FortiGate → device layer) — they do not update the policy package because retrieving only captures state; an explicit Import operation is required to move a retrieved revision into a policy package.
Q2 — MODEL ANSWER
Quick Install applies the device layer config to FortiGate immediately without showing an installation preview. Install Device Settings shows you the diff first so you can review and cancel. Use Quick Install for ZTP/automation or when you're confident about the changes — the tradeoff is losing the review checkpoint that Install Device Settings provides.
Q3 — MODEL ANSWER
Quick Install pushes device layer settings (interfaces, routing, system config) from the device database directly to FortiGate. It does NOT push the policy package. The firewall policy changes will not be deployed. The engineer needs to use Install Policy Package instead. This is one of the most common Quick Install misuses on the exam.
Q4 — MODEL ANSWER
No. Auto-Retrieve only updates the device layer database in FortiManager — it captures the current FortiGate configuration and saves it as a new revision. The policy package is not touched. Policy package status remains whatever it was before the retrieve. To move retrieved policies into a policy package, you must run a separate Import operation.

Configuration Operations

Each arrow has a short label. No shadows, clean educational infographic.

Eight configuration operations — each moves data in a specific direction between FortiGate, the device layer, and the policy layer.

OperationDirectionKey Behaviour
Retrieve FortiGate → Device Layer Manually captures current FortiGate config as a new revision. Does not update the policy package.
Auto-Retrieve FortiGate → Device Layer Triggered automatically when a FortiGate is added. Captures changes from the firewall into revision history. Does not update the policy package — Import is required for that.
Install Device Settings Device Layer → FortiGate Applies device layer config to FortiGate. Offers an installation preview to review changes before committing.
Quick Install Device Layer → FortiGate Same as Install Device Settings but without a preview. Applies immediately. Ideal for ZTP or trusted changes.
Revert Revision History (internal) Selects an earlier revision for potential import or installation. Synchronizing device and policy layers afterward requires a subsequent Import.
Import Device Layer → Policy Layer Moves policies from a selected revision into the policy package. Care needed to avoid importing objects that already exist with the same name in the policy layer.
Install Policy Package Policy Layer → Device Layer + FortiGate Transfers the policy package from policy layer to both the device layer and FortiGate. Displays a step-by-step wizard with installation preview and cancel option.
Reinstall Policy Policy Layer → FortiGate Bypasses the wizard (device and policy package already selected). Offers installation preview. Also applies any direct modifications in the device database, not just policy package settings.
Import conflict trap: If an object with the same name already exists in the policy layer, FortiManager must choose between the FortiGate value and its own — causing a conflict. Always audit for duplicate object names before importing.
⚑ NSE7 — Direction test: Retrieve and Auto-Retrieve are inbound (FortiGate → FortiManager) and only touch the device DB. Every install operation is outbound (FortiManager → FortiGate). Mnemonic: Retrieve pulls, Install pushes. If an exam question says "Retrieve updated the policy package," that is false.
🧠
MENTAL NOTE
Retrieve/Auto-retrieve: FortiGate → Device Layer only (no policy package update). Install/Quick Install: Device Layer → FortiGate (Quick = no preview). Import: Device Layer → Policy Layer. Install Policy Package: full wizard + preview. Reinstall Policy: no wizard, has preview, also applies device DB modifications.

💭 THINK FIRST · GLOBAL PROVISIONING

The global ADOM can push the same policy to every ADOM in two different ways — one requires no further steps, while the other puts the policy into a "modified" state requiring admin action. Provisioning templates work differently again, overriding device layer settings automatically on assignment.

  • What is the difference between "Automatically Install Policies to ADOM Devices" and "Assign" for global policy distribution?
  • Why do provisioning templates take precedence over other device layer settings — and why is that significant?
  • A Global ADOM is running FortiOS 7.6. Which local ADOM firmware versions are compatible with it, and why is the "g" prefix significant when distributing global objects?
Q1 — MODEL ANSWER
"Automatically Install Policies to ADOM Devices" pushes the global policy package directly to the policy layer, device layer, and FortiGate in one step with no additional admin action — but it bypasses the installation preview. "Assign" only updates the policy layer, marking the package as Modified; an admin must then manually install or reinstall the policy to complete the push to FortiGate. Assign gives you a review checkpoint; Auto-Install does not.
Q2 — MODEL ANSWER
Provisioning templates have precedence over other device layer settings, meaning they can overwrite values already in the device database when assigned. This is significant because it means assigning a template to an existing device can silently change configurations you already have — for example, overwriting interface IPs. Always plan template assignments deliberately and preview before assigning in production.
Q3 — MODEL ANSWER
A Global ADOM at 7.6 supports local ADOMs at the same version and two minor versions earlier: 7.6, 7.4, and 7.2. Anything older than 7.2 is not compatible. The "g" prefix is reserved — FortiManager automatically prefixes every global object with "g", and no custom object in any local ADOM may start with "g". This guarantees there is never a naming collision between a global object and a local object during distribution.

Global Policy Package and Provisioning

Global policy packages reach local ADOMs via Auto-Install (immediate, no preview) or Assign (Modified status, requires manual install to complete).

The Global Policy Package is managed in the global ADOM and distributed to multiple local ADOMs to enforce consistent security baselines. Two distribution methods exist:

  • Automatically Install Policies to ADOM Devices: The global ADOM directly installs the assigned policy package to the policy layer, device database, and FortiGate simultaneously. No additional admin steps required, but the installation preview is bypassed.
  • Assign: Updates the policy layer only, marking status as Modified. Admins must then install or reinstall the policy package to push to the device layer and FortiGate. This provides a review checkpoint before production impact.

The same global ADOM can distribute identical global policies to different local ADOMs simultaneously.

Device layer ADOM capabilities include provisioning templates, Fabric View, and Extender Manager. Provisioning templates have precedence over standard device layer settings — when assigned, they automatically overwrite the device layer database for each FortiGate. They are applied using Install Device Settings or Quick Install.

Policy layer ADOM capabilities include VPN Manager, AP Manager, and FortiSwitch Manager. These set up normalized interfaces such as zones, VLANs, and SSIDs. After configuring these features, changes require a policy package install or reinstall to reach FortiGate.

Best practice: Use Assign (not Auto-Install) for global policy rollouts in production — the installation preview gives you a final safety checkpoint before changes touch the firewalls.
⚑ NSE7 — Compatibility rule: A Global ADOM at version 7.6 supports local ADOMs at 7.6, 7.4, and 7.2 (same version + two minor versions earlier). ADOMs older than 7.2 are not compatible with a 7.6 global ADOM.
🧠
MENTAL NOTE
Auto-Install = immediate to all layers, no preview. Assign = Modified status only, manual install required. Provisioning templates override device layer (deploy via device install). VPN/AP/FortiSwitch Manager are policy-layer features — require policy package install to apply.
