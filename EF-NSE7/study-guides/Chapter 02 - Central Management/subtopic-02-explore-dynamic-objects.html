Explore Dynamic Objects

Normalized interfaces, per-device and per-platform mapping, mapping conflicts, and metadata variables — how FortiManager applies a single policy template across diverse hardware.

One policy, many firewalls — dynamic objects are how FortiManager makes that work without duplicating every rule.

The exam tests whether you know which objects support per-device mapping and what happens when they don't — conflict scenarios are common question territory.

💭 THINK FIRST · NORMALIZED INTERFACES

FortiManager uses a single policy package across many FortiGate models — but every model has different physical interface names (port1, port3, lan, wan1). Without a way to abstract these differences, you'd need a separate policy package for every hardware model. Normalized interfaces solve this.

  • What is a normalized interface, and what two mapping methods does FortiManager provide?
  • Why are normalized interfaces case-sensitive, and in which layers can they be assigned?
Q1 — MODEL ANSWER
A normalized interface is an abstract interface name defined in FortiManager that maps to actual physical interface names on individual FortiGate devices. It lets you write a single policy using the abstract name (e.g., "LAN") and FortiManager translates it to the correct physical port per device. Two mapping methods: per-platform (uniform mapping across all devices of the same model) and per-device (customized mapping for an individual device).
Q2 — MODEL ANSWER
Normalized interfaces are case-sensitive because they are matched as strings — "LAN" and "lan" are treated as two completely different interfaces, which can cause unexpected behavior if inconsistent naming is used. They can be assigned in both the policy layer and the device layer, giving you flexibility to apply normalization at either level depending on your use case.

A normalized interface (e.g., "LAN") maps to different physical ports per platform or per device — FortiManager translates the name automatically at install time.

The Normalized Interfaces feature (found at Policy & Objects → Normalized Interfaces) standardizes interface naming across devices for easier management. Instead of writing separate policies per hardware model, you define an abstract interface name and map it to actual ports on each device.

Two mapping methods are available:

  • Per-platform mapping: Applies a uniform interface mapping across all devices of the same hardware model. Example: all FortiGate-500E devices map "LAN" to port3.
  • Per-device mapping: Allows customized interface mapping for a specific individual device. Example: FortiGate-VM64 at HQ maps "LAN" to port4.

Using normalized interfaces does not automatically change the interface names on the FortiGate. When FortiManager references "LAN" in a policy and it is configured as a normalized interface mapped to port4, the actual interface name on FortiGate remains port4 — FortiManager substitutes it during install. You must approve the substitution in the installation preview.

Critical exam point: normalized interfaces are case-sensitive. "LAN" and "lan" are treated as completely different interfaces. Use consistent naming across device layer and policy layer to avoid hard-to-diagnose assignment issues. Normalized interfaces can be assigned in both the policy layer and the device layer.

Naming pitfall: Using a normalized interface to replace an original interface name means FortiManager will substitute that name with the mapped port in all policies for that device. Keep names consistent — per-device mapping silently overrides whatever the policy layer specifies for that firewall.
🧠
MENTAL NOTE
Normalized interfaces: per-platform (all same-model devices) vs. per-device (one specific device). Case-sensitive — "LAN" ≠ "lan." Assigned in both policy layer and device layer. FortiManager substitutes the abstract name with the real port at install time.

💭 THINK FIRST · PER-DEVICE MAPPING

Per-device mapping extends beyond interfaces — it also applies to firewall address objects. This lets Branch1 and Branch2 share the same policy and the same object name "LAN_SUBNET" while each resolving to a completely different IP range behind the scenes.

  • What types of objects support per-device mapping, and why does it matter which do and which don't?
  • If two branches need different web filter settings, but web filter profiles don't support per-device mapping, what is the correct approach?
Q1 — MODEL ANSWER
Objects that support per-device mapping include firewall address objects (Addresses, Virtual IPs, IP Pools), certain user and authentication objects (User Groups, LDAP Servers, RADIUS Servers, TACACS+), FortiNAC, FortiSingle Sign-On Agent, metadata variables, and dynamic local certificates. It matters because objects that don't support per-device mapping cannot have different values per firewall under the same name — if you try to use the same object name for two different configs in the policy layer, FortiManager has to choose one, causing a conflict.
Q2 — MODEL ANSWER
Since web filter profiles don't support per-device mapping, you cannot differentiate them per device under the same profile name. The correct approach is to create uniquely named web filter profiles for each variation — for example "webfilter-branch1" and "webfilter-branch2" — and reference the correct profile in each device's policy. This is the only way to achieve different configurations without triggering a policy layer conflict.

Per-Device Mapping for Objects

The same "LAN" address object maps to different IP ranges on Branch1 vs. Branch2 — per-device mapping handles the difference under one shared object name.

Beyond interfaces, per-device mapping can be applied to a range of object types, allowing the same object name to resolve to different values for each managed FortiGate. This is the mechanism that lets a single policy package work across firewalls with different network configurations.

Three categories of dynamic configuration in FortiManager:

  • Interface mapping — normalized interfaces (covered in the previous section)
  • Object per-device mapping — address objects, VIPs, IP pools, user groups, LDAP/RADIUS/TACACS+ servers, FortiNAC, metadata variables, dynamic local certificates, dynamic VPN tunnels
  • Metadata variable mapping — dynamic values inserted into object fields using the $ prefix (covered in Section 04)

Example: The firewall address object named LAN can be configured with per-device mapping so Branch1 resolves to 172.16.0.0/24 and Branch2 resolves to 192.168.0.0/24. Both branches use the same policy referencing "LAN," and FortiManager substitutes the correct range at install time.

Important restriction: Not all objects support per-device mapping. Security profile objects (Web Filter, Antivirus, Application Control, IPS, DNS Filter, etc.), most User & Authentication objects (User Definitions, POP3 Users, FortiTokens, SMS Server), and most Security Fabric connectors do not support it. For these, you must create uniquely named objects for each variation.
🧠
MENTAL NOTE
Per-device mapping supports: address objects, VIPs, IP pools, user groups, LDAP/RADIUS/TACACS+ servers, metadata variables, dynamic certs. Does NOT support: security profiles (web filter, AV, IPS, AppCtrl), Internet Service, network services, most auth servers. If unsupported, create uniquely named objects per device.

💭 THINK FIRST · MAPPING CONFLICTS

When FortiManager imports a configuration from a device, it may encounter an object in the device database that shares a name with an object already in the policy layer — but with different values. FortiManager can't have two different objects with the same name in the policy layer, so it is forced to choose between them.

  • What causes a per-device mapping conflict during import, and what does FortiManager do when it encounters one?
  • What is the correct resolution when a conflict occurs?
Q1 — MODEL ANSWER
A conflict occurs when you import a configuration from the device layer and the policy layer already has an object with the same name but configured for per-device mapping that the policy layer doesn't support — or with a different value the policy layer can't reconcile. FortiManager is forced to choose between the FortiGate's value and its own existing policy layer value. This is why it's important to know which objects support per-device mapping before importing.
Q2 — MODEL ANSWER
The resolution is to create a uniquely named object on FortiGate for the conflicting configuration, then import it again. With a unique name, FortiManager can add it to the policy layer without colliding with the existing object. This is the only clean way to resolve the conflict — trying to overwrite the existing object risks breaking other devices that reference it.

Objects that support per-device mapping can share a name across devices with different values; objects that don't require unique names per variation to avoid conflicts.

Understanding which objects support per-device mapping is critical because importing a configuration from a device that has an object with the same name as an existing policy layer object — for a type that doesn't support per-device mapping — forces FortiManager to choose between the FortiGate value and its own value. This creates a conflict.

Available (support per-device mapping):

  • Firewall Objects: Addresses, VIPs, Virtual IP Groups, IPv4/IPv6 Pools, Virtual Server & IPv6 Virtual Server, ZTNA Server & IPv6 ZTNA Server
  • Security Profiles: N/A (none supported)
  • User & Authentication: User Groups, LDAP Servers, RADIUS Servers, TACACS+
  • Security Fabric: FortiNAC, Fortinet Single Sign-On Agent
  • Advanced: Metadata Variables, Dynamic Local Certificate, Dynamic VPN Tunnel

Unavailable (no per-device mapping — require unique names per device for different configs):

  • Firewall Objects: Internet Service, Services & Service Groups, Schedules, Network Service, IP Pool Group, Shared Traffic Shapers & Per-IP Traffic Shapers
  • Security Profiles: Antivirus, Web Filter, Video Filter, DNS Filter, Application Control, IPS, SSL Inspection, ICAP, Web Application Firewall, Data Loss Prevention, Virtual Patching, Email Filter, and many more
  • User & Authentication: User Definitions, POP3 Users, FortiTokens, PKI User & Groups, SMS Server
  • Security Fabric: most connectors including NSX-T, vCenter, Public/Private SDN, ClearPass
  • Advanced: Replacement Message Group

Conflict resolution: If a conflict occurs, create a uniquely named object on FortiGate for the conflicting configuration, then import it again to the policy layer. With a unique name, FortiManager can add it without collision.

Exam strategy: It's worth memorizing the key categories that do support per-device mapping (address objects, IP pools, VIPs, user groups, auth servers, metadata variables) — the rest almost certainly don't. When in doubt on an exam scenario, if it's a security profile, it doesn't support per-device mapping.
🧠
MENTAL NOTE
Conflict = same object name, different value, unsupported type → FortiManager must choose. Resolution = create unique name on FortiGate, re-import. Memorize: address objects and auth servers support mapping; security profiles and most fabric connectors do not.

💭 THINK FIRST · METADATA VARIABLES

Per-device mapping lets you vary a whole object per device. But sometimes you only want to vary a single field within an object — like the IP/Netmask of a firewall address. Metadata variables let you do exactly that, using a $ prefix to mark a field as dynamic.

  • Where are metadata variables created, and in what two contexts can they be used?
  • How do you activate a metadata variable inside a firewall object field in the FortiManager GUI?
Q1 — MODEL ANSWER
Metadata variables are created and edited in the policy layer, at Policy & Objects → Advanced → Metadata Variables. They can be used in two contexts: within provisioning templates (to inject device-specific values during ZTP/LTP) and within policy layer objects (e.g., as the IP/Netmask value of a firewall address object). They support per-device mapping, so each device can have a different value for the same variable.
Q2 — MODEL ANSWER
To activate a metadata variable inside a field, type the $ character in the field. A pop-up window appears showing available variables (or a + button to create a new one). The GUI indicates fields that support metadata variables with a magnifying glass icon containing a $ symbol. You then select the variable and it becomes the field value — FortiManager substitutes the per-device value at install time.

The $ symbol activates metadata variable mode in a compatible field — FortiManager substitutes the per-device value for that variable at install time.

Metadata variables are dynamic placeholders used to inject device-specific values into object fields and provisioning templates. They are created and edited in the policy layer at Policy & Objects → Advanced → Metadata Variables.

Two usage contexts:

  • Provisioning templates: Variables provide dynamic values during ZTP and LTP device onboarding — for example, injecting the correct IP address range for each new site's LAN interface automatically.
  • Policy layer objects: Variables can be used as the value of specific object fields — for example, the IP/Netmask field of a firewall address object named "LAN_SUBNET" can reference $Area, which resolves to a different subnet per device.

The GUI identifies metadata-capable fields with a magnifying glass icon containing a $ symbol. To use a variable, type $ in the field — a pop-up lists existing variables and a + button to create new ones. If the variable doesn't exist yet, click + to define it with a name, default value, and description.

Metadata variables support per-device mapping, so each FortiGate can have a different value for the same variable. A default value provides a fallback for devices without a specific mapping configured. Variables can also be used in CLI templates and pre-run CLI templates for scripted provisioning.

Provisioning power: Combining metadata variables with CLI templates lets you deploy a full site configuration to a new FortiGate with zero manual input — each device gets the correct IPs, subnets, and settings injected from its variable mapping automatically.
🧠
MENTAL NOTE
Metadata variables: created in Policy & Objects → Advanced → Metadata Variables (policy layer). Used in: provisioning templates AND policy layer object fields. Activated by typing $ in a compatible field (magnifying glass + $ icon). Support per-device mapping with a default fallback value.
