Route Redistribution & BGP Convergence

Master cross-protocol redistribution, BGP convergence optimization techniques (RIB sizing, route reflectors, BFD, graceful-restart), and the role each plays in maintaining a stable, fast-converging enterprise network.

Redistribution is where routing protocols talk to each other — and where misconfigurations create the routing loops that bring down networks.

This subtopic ties together the redistribution mechanics of both OSPF and BGP, then covers the full BGP convergence optimization toolkit: RIB filtering, route reflectors, BFD, and graceful-restart for HA environments.

💭 THINK FIRST · CROSS-PROTOCOL REDISTRIBUTION

Route redistribution is how different routing protocols share information — but it comes with a fundamental risk: routing loops. When Router A redistributes OSPF into BGP, and Router B redistributes BGP back into OSPF, routes can loop infinitely. Both protocols disable redistribution by default — this is a safety mechanism, not an oversight.

  • If you redistribute OSPF routes into BGP and then redistribute BGP routes back into OSPF on the same router, what happens — and how do you prevent the loop?
  • What is the difference between configuring a "network" statement in OSPF versus using "redistribute connected" — specifically, what LSA type does each produce and how does this affect path preference?
Q1 — MODEL ANSWER
A mutual redistribution loop occurs: OSPF routes become BGP routes, which get redistributed back into OSPF as external routes — creating duplicate entries with different metrics. The prevention tool is a route map with a tag: when redistributing OSPF into BGP, tag the routes; when redistributing BGP back into OSPF, use a route map to deny routes with that tag. This prevents the loop without blocking legitimate routes from other sources.
Q2 — MODEL ANSWER
A "network" statement makes the prefix an intra-area OSPF route — it appears in the LSDB as a Type 1 or Type 2 LSA and is treated as internal OSPF topology. "Redistribute connected" imports the connected prefix as an external route — it appears as a Type 5 LSA (or Type 7 in NSSA), tagged as "E" in routing tables, and carries an external metric. OSPF prefers internal routes over external routes regardless of cost — so a network statement route will always beat a redistribute-connected route if both exist in the domain.

Redistribution flows routes between protocols. Mutual redistribution without loop-prevention (route maps + tags) creates routing loops.

Route redistribution allows a router to take routes learned in one protocol and inject them into another. Both OSPF and BGP disable all redistribution by default — every protocol source (bgp, connected, isis, rip, static) must be explicitly enabled. This conservative default prevents accidental route injection.

Key redistribution concepts for both OSPF and BGP:

  • OSPF redistribution: routes imported via redistribution appear as Type 5 LSAs (external); configured in config router ospf → config redistribute
  • BGP redistribution: connected, static, and IGP routes can be redistributed into BGP via config router bgp → config redistribute
  • Mutual redistribution: when routes are redistributed in both directions between two protocols, route maps with tags are required to prevent feedback loops

FortiGate CLI — Enabling OSPF Redistribution
# Enable redistribution of connected and static into OSPF:
config router ospf
    config redistribute connected
        set status enable
    end
    config redistribute static
        set status enable
    end
end

# Enable redistribution of connected and static into BGP:
config router bgp
    config redistribute connected
        set status enable
    end
    config redistribute static
        set status enable
    end
end
Loop prevention: When doing mutual redistribution (OSPF ↔ BGP), use a route map to tag routes at the redistribution boundary, then deny routes with that tag when redistributing in the reverse direction. Without this, routes circulate between protocols indefinitely.

Mutual redistribution needs route-map + tag to prevent loops. OSPF intra-area always preferred over external regardless of metric.

💭 THINK FIRST · BGP CONVERGENCE

BGP convergence has multiple independent contributors — RIB size, update processing speed, failure detection latency, and HA behavior. Each requires a different optimization tool. Port flapping is particularly damaging because it generates BGP update messages that consume CPU, destabilizing convergence across the network.

  • The study guide states that port flapping "creates BGP update messages that require RIB processing and add to CPU load." Why does flapping on ONE interface generate update messages that affect ALL BGP peers?
  • Why is "optimize the RIB size" listed as a convergence optimization? Isn't a bigger RIB with more routes better for routing accuracy?
Q1 — MODEL ANSWER
BGP is a path-vector protocol that sends its routing table to all neighbors. When an interface flaps, the routes reachable through it change — BGP must generate UPDATE messages (both withdrawal and re-advertisement) and send them to every configured BGP peer. Each peer then processes the update, recalculates best paths, and may generate its own updates. A single flapping interface can cascade update messages across the entire AS and into eBGP peers, creating a CPU and bandwidth avalanche.
Q2 — MODEL ANSWER
A larger RIB means more entries to process during each update cycle. When a topology change occurs, BGP must re-evaluate best paths for every affected prefix — the larger the RIB, the longer this takes. By using inbound filters (distribute-list-in, prefix-list-in) to exclude routes that are not needed locally, you reduce the number of prefixes that must be re-processed on every update, directly improving convergence speed. Routing accuracy is maintained because the filtered routes are still reachable via default or aggregate routes.

BGP Convergence Optimization

images/s2-bgp-convergence.png

Four levers for BGP convergence: RIB size reduction, route reflectors, BFD for failure detection, and graceful-restart for HA.

BGP convergence is the process of updating routing and forwarding tables after a topology change. BGP sends its entire routing table to directly connected neighbors — the larger the RIB and the more neighbors there are, the longer convergence takes. Four main optimization areas exist:

  • Optimize RIB size — use inbound and outbound filters to exclude unnecessary prefixes. A smaller RIB means fewer paths to recompute on each update cycle.
  • Route Reflectors — in iBGP, route reflectors eliminate the full-mesh requirement, reducing the number of BGP sessions and concentrating update processing.
  • Fast failure detection — reduce BGP keepalive timers or enable BFD. BFD can detect failures in sub-second timeframes vs. BGP's default timer-based detection.
  • HA failover stability — configure graceful-restart to prevent unnecessary BGP session resets and route withdrawals during planned HA failovers.
Root cause: Port flapping is the most common enemy of BGP convergence. Each flap generates withdrawal + re-advertisement messages to all peers, consuming CPU for RIB reprocessing. Stable physical links are a prerequisite for fast BGP convergence.
Analogy

BGP convergence is like an airline updating its departure boards — a single gate change cascades through every connected display in the network.

  • BGP RIB — the master flight schedule board that every gate display reads from
  • Port flapping — a gate being repeatedly opened and closed, triggering board updates for every connecting flight
  • Inbound filter (RIB optimization) — only displaying the flights relevant to this terminal, not every flight in the world
  • Route Reflector — a central "hub display" that other terminals read from, instead of every terminal talking to every other terminal
  • BFD — a sensor at the gate that instantly detects when the jetway disconnects, vs. waiting for a scheduled check-in timer

💭 THINK FIRST · ROUTE REFLECTORS

iBGP's split-horizon rule requires all iBGP routers to be fully meshed — N routers need N×(N-1)/2 sessions. In large ASes this is operationally unmanageable. Route reflectors solve this by designating one or more routers as concentrators that re-advertise iBGP routes to clients — breaking the full-mesh requirement.

  • A route reflector forwards routes learned from one peer to other peers — this appears to break the iBGP split-horizon rule. Why doesn't this create routing loops?
  • The study guide recommends configuring TWO route reflectors (RR1 and RR2). What would happen if only one route reflector existed and it failed?
Q1 — MODEL ANSWER
Route reflectors use the CLUSTER_LIST and ORIGINATOR_ID BGP attributes as loop-prevention mechanisms. When the RR reflects a route, it adds its cluster ID to the CLUSTER_LIST. If a reflected route returns to the RR, it will see its own cluster ID in the list and discard the route — preventing loops. The RR also adds the ORIGINATOR_ID of the originating router, which prevents a router from accepting routes it originally sent.
Q2 — MODEL ANSWER
With a single route reflector, all iBGP route distribution within the AS depends entirely on that one router. If it fails, no iBGP routes are distributed — effectively partitioning the AS. Routers can only reach directly connected neighbors. Two route reflectors provide redundancy: each reflects routes independently, and clients can maintain sessions to both, ensuring iBGP connectivity survives a single RR failure.

iBGP Route Reflectors

Route reflectors eliminate the iBGP full mesh — clients peer only with the RR, which reflects routes between all clients.

In a fully-meshed iBGP network, every router must peer with every other router — N routers need N×(N-1)/2 BGP sessions. This scales poorly. Route Reflectors (RRs) solve this by acting as iBGP concentrators: each iBGP client peers only with the RR, and the RR forwards (reflects) routes learned from one client to all other clients.

The RR is configured by designating which neighbors are route-reflector clients. The RR itself defines the topology — it decides which neighbors are clients. Non-client iBGP peers must still form a full mesh between themselves (and between RRs). Loop prevention is handled via CLUSTER_LIST and ORIGINATOR_ID attributes added automatically by the RR.

FortiGate CLI — Configure Route Reflector
config router bgp
    config neighbor
        edit 100.64.1.254
            set next-hop-self enable
            set route-reflector-client enable
        next
    end
end

# Verify:
get router info bgp neighbors

Key deployment guidelines for route reflectors:

  • Deploy at least two RRs per cluster for redundancy
  • Enable next-hop-self on the RR so clients use the RR as the next hop — prevents next-hop unreachability when the original next hop is an eBGP peer
  • RRs pass routing updates to other RRs and border routers within the AS, improving convergence
  • RRs eliminate the administrative burden of managing a full mesh — critical in large enterprise or SP networks with dozens or hundreds of iBGP speakers
Configuration note: The RR does NOT announce itself as a route reflector — it simply marks certain neighbors as clients with "route-reflector-client enable". The clients don't know they're peering with an RR; they just see a regular iBGP neighbor that happens to send them all routes.
🧠
MENTAL NOTE
iBGP full mesh = N×(N-1)/2 sessions. Route Reflector = concentrator; clients peer only with RR. Configure with "set route-reflector-client enable" on client neighbors. Loop prevention = CLUSTER_LIST + ORIGINATOR_ID. Always deploy 2 RRs for redundancy. Enable next-hop-self on RR.

💭 THINK FIRST · BFD FOR FAST FAILURE DETECTION

BGP relies on keepalive timers for failure detection — by default, a peer is considered dead only after the hold-down timer expires (typically 90 seconds). BFD runs independently of BGP and can detect failures in under one second. This is a massive convergence improvement, but BFD has configuration requirements — particularly for multihop sessions where the BFD probe must traverse multiple routers.

  • BFD is described as "independent of the type of media" — what does this mean for its usefulness compared to link-layer failure detection like Ethernet carrier-detect?
  • For BFD on a multihop BGP session (like a loopback-sourced session), a "multihop-template" is required. Why can't the same single-hop BFD mechanism work for multihop paths?
Q1 — MODEL ANSWER
Ethernet carrier-detect only works for direct physical link failures — it cannot detect failures through intermediate devices, tunnels, or logical failures (like a misconfigured router that forwards but drops certain packets). BFD sends bidirectional probe packets end-to-end between the two BFD peers, so it detects any failure along the entire path — a failed intermediate router, a black-hole condition, or a forwarding loop. This makes it useful for GRE tunnels, MPLS paths, and any topology where intermediate devices could silently fail.
Q2 — MODEL ANSWER
Single-hop BFD assumes both endpoints are directly connected on the same subnet and uses a specific TTL/hop-limit to verify this. Multihop BFD sessions traverse intermediate routers, requiring different IP addresses (not link-local) and cannot rely on single-hop TTL assumptions. The multihop-template provides the source and destination IP ranges and authentication settings that allow BFD to correctly identify and authenticate the multihop session — distinguishing it from other BFD sessions that may share the same physical path.

BFD — Bidirectional Forwarding Detection

Right panel "Multihop BFD": three routers in a chain; BFD probe shown as a dashed green beam traversing all three, with a "multihop-template" badge. BFD detects failures in under 1 second, independently of BGP timers. Multihop BFD requires a multihop-template for paths across intermediate routers.

Bidirectional Forwarding Detection (BFD) is a protocol that acts as a lightweight "heartbeat" probe between two routers. It operates independently of BGP and can detect one-way device failures in less than one second — far faster than BGP's keepalive-based detection which typically takes 90 seconds. BFD is media-independent: it works the same over Ethernet, MPLS, GRE tunnels, or any IP path.

For standard BGP sessions (direct neighbors), BFD is enabled per-neighbor with a single command. The BFD session is established automatically when both routers have BFD enabled on the session.

FortiGate CLI — BFD on a BGP Neighbor (Single-Hop)
config router bgp
    config neighbor
        edit 100.64.1.254
            set bfd enable
            set ebgp-enforce-multihop enable
        next
    end
end

# Verify BFD status:
get router info bfd neighbor

For multihop BGP sessions (e.g., loopback-sourced eBGP), BFD requires a multihop-template that specifies the source and destination IP ranges and optional authentication:

FortiGate CLI — BFD Multihop Template
config router bfd
    config multihop-template
        edit 1
            set src 100.64.2.0 255.255.255.0
            set dst 100.64.1.0 255.255.255.0
            set auth-mode md5
            set md5-key password
        next
    end
end

BFD must be configured on both connected routers and their corresponding interfaces. For multihop paths, the template must be configured on both ends with matching source/destination ranges.

Exam tip: BFD detects failures in <1 second. BGP's default keepalive = 60 seconds; hold-down = 180 seconds. BFD is independent of media type. Multihop BFD requires a multihop-template specifying src/dst IP ranges. Verify with "get router info bfd neighbor".
🧠
MENTAL NOTE
BFD = sub-second failure detection, media-independent. Single-hop: set bfd enable per neighbor. Multihop (loopback BGP): requires "config router bfd → config multihop-template" with src/dst IP ranges + optional auth. Must enable on BOTH routers. Verify: "get router info bfd neighbor".

💭 THINK FIRST · GRACEFUL RESTART

BGP graceful-restart is designed specifically for HA failover scenarios. When an HA cluster fails over, the BGP daemon must restart on the new primary — and peers would normally interpret this as a session failure, withdrawing routes. Graceful-restart prevents this by pre-announcing the intent to restart, causing peers to keep routes stale (but usable) during the reconnection window.

  • Graceful-restart must be configured on BOTH connected routers. What happens if only one router has graceful-restart enabled — does it still work?
  • Graceful-restart is described as preventing routes from being "treated as a route flap." What is the practical traffic impact of a route flap during an HA failover, and why does graceful-restart prevent it?
Q1 — MODEL ANSWER
Graceful-restart requires both sides to negotiate the capability. If only one router has it enabled, the router with graceful-restart will advertise the capability, but the peer will not acknowledge it. Without mutual negotiation, graceful-restart does not activate — both sides must understand and agree to the graceful-restart procedure for it to take effect during failover. This is why capability-graceful-restart must also be enabled on the neighbor configuration, so the capability is explicitly advertised to the peer.
Q2 — MODEL ANSWER
Without graceful-restart, when the HA primary fails and the session drops, the BGP peer removes all routes learned from that session — traffic to those destinations is immediately dropped or rerouted via less-optimal paths. The new HA primary must re-establish the session and re-advertise all routes before traffic is restored. With graceful-restart, the peer keeps the routes marked as "stale but valid" during the restart window — traffic continues to forward normally while the new primary reconnects and refreshes the routes.
SECTION 05

The graceful-restart Command — HA Failover Protection

images/s5-graceful-restart.png

Right panel "With graceful-restart": HA cluster advertises "going offline" → peer marks routes "stale but valid" → new primary reconnects → routes refreshed (green checkmark, traffic continues). Time arrow shows shorter interruption with graceful-restart. Bold outlines, pastel red/green palette, educational style, no shadows.

Graceful-restart prevents BGP peers from withdrawing routes during HA failover — routes remain usable while the new primary reconnects.

In a FortiGate HA cluster, the BGP daemon runs only on the primary unit. When the primary fails and a secondary takes over, BGP peering must be re-established from scratch. Without graceful-restart, peers interpret the session drop as a failure and immediately withdraw all routes received from the cluster — creating a traffic blackhole until the new primary reconnects and re-advertises.

The graceful-restart command allows the FortiGate HA cluster to advertise its intent to restart before going offline. Peers honor this by keeping routes in their routing tables as stale (but still forwarding-capable) for the duration of the restart window. When the new primary comes online, it re-establishes the session and refreshes the routes — without causing a traffic disruption.

FortiGate CLI — Graceful Restart Configuration
config router bgp
    set as 65100
    set graceful-restart enable
    set router-id 172.16.1.254
    config neighbor
        edit 100.64.1.254
            set capability-graceful-restart enable
            set remote-as 200
        next
    end
end

Two parameters work together for graceful-restart:

  • set graceful-restart enable — enables the graceful-restart feature globally on the BGP router
  • set capability-graceful-restart enable — per-neighbor setting that advertises the graceful-restart capability to the specific BGP peer so both sides negotiate the behavior
Critical requirement: Both "graceful-restart enable" AND "capability-graceful-restart enable" must be configured. The global command enables the feature; the per-neighbor command advertises the capability to the peer. Without both, graceful-restart doesn't activate. Must also be configured on the BGP peer.
Maintenance window benefit: Graceful-restart is particularly valuable during planned maintenance (firmware upgrades, HA testing) — the cluster advertises its restart intent, peers keep routes valid, and traffic interruption is minimized or eliminated entirely.
🧠
MENTAL NOTE
Graceful-restart: 2 commands required — "set graceful-restart enable" (global) + "set capability-graceful-restart enable" (per-neighbor). Must be on BOTH routers. Prevents routes from being withdrawn during HA failover. Routes stay "stale but valid" while new primary reconnects. Critical for planned maintenance windows.
