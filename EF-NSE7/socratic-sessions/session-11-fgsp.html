Pre-Reading Story

"Half the Packets Are Lost — But Why?"

A regional ISP deployed two FortiGate units at their network edge to handle internet gateway traffic for their subscriber base. To maximize throughput, the upstream routing was configured with Equal-Cost Multi-Path (ECMP) load sharing, splitting traffic across both FortiGates based on a per-flow hash. In most scenarios, a single TCP session would stay on one FortiGate for its entire lifetime. But in practice, the flow hashing wasn't always consistent for every subscriber, and occasionally a session's forward path and return path were split across the two devices. FortiGate-1 would see the initial SYN from a subscriber and create a session table entry. The SYN-ACK from the server would return via a different BGP path, arriving at FortiGate-2. FortiGate-2 had no record of this session. It had never seen the SYN. The packet looked like an unsolicited inbound connection attempt, and it was dropped as invalid.

Subscribers started reporting random connection failures. Downloads would start and then stall midway. VoIP calls dropped without warning. The ISP's helpdesk call volume doubled. The engineering team pulled packet captures and immediately saw thousands of TCP RST packets originating from the FortiGate layer. The pattern was clear once they mapped the flows to the routing table: every dropped session was one where forward and return traffic had been routed to different FortiGate units. The stateful firewall behavior that made FortiGate excellent at security was causing it to drop half the packets in an asymmetric routing environment — because a stateful firewall enforces the rule that it must see both directions of a session to consider it valid.

The solution was FGSP — FortiGate Session Life Support Protocol. Unlike FGCP, which creates a cluster with shared identity and a primary/secondary relationship, FGSP allows two completely independent FortiGate units to synchronize their session tables with each other. Each unit retains its own management IP, its own routing table, its own configuration, and its own forwarding plane. But the session tables are shared in near real time. When FortiGate-1 establishes a new TCP session, it pushes that session entry to FortiGate-2's session table as well. When the return packet arrives at FortiGate-2, there is now a matching session entry — the packet is accepted and forwarded. The TCP RST storms ceased. Downloads completed. VoIP calls stabilized. FGSP had resolved an asymmetric routing problem that FGCP could not address, because FGCP requires traffic to converge on a single primary unit.

Overview

FGSP — Session Sync for Independently-Operating FortiGates

The FortiGate Session Life Support Protocol (FGSP) addresses a problem that FGCP cannot: what happens when network topology forces traffic to flow asymmetrically across multiple FortiGate units? In an FGCP cluster, all traffic converges on the primary unit — asymmetric flows don't exist by design. But in carrier-grade networks, data center fabrics using ECMP routing, or any environment where the path of a packet's return journey cannot be guaranteed to match its forward journey, a stateful firewall without session synchronization will drop traffic. FGSP solves this by sharing the session table between two FortiGate units that otherwise operate completely independently.

The critical distinction between FGSP and FGCP is the degree of coupling between the participating devices. In FGCP, the two units form a cluster — they share a cluster identity, one is primary and the other is secondary, configurations are synchronized, and failover is automatic. In FGSP, each FortiGate retains its own complete identity: its own hostname, its own management IP, its own routing table, its own policy database, and its own configuration. FGSP does not synchronize configurations — it only synchronizes session state. This means you can run two FortiGates with entirely different configurations in an FGSP pair, which can be useful but also means there is no automatic failover — if one unit fails, the other continues processing traffic but does not automatically take over the failed unit's responsibilities.

Configuring FGSP requires defining the peer unit's IP address on each FortiGate, enabling session synchronization, and optionally configuring filters to limit which session types are synchronized. Not every session needs to be synchronized — in a high-throughput environment, synchronizing short-lived DNS sessions would create unnecessary overhead. Most deployments synchronize only long-lived TCP sessions and omit UDP sessions below a configurable duration threshold. FGSP can also be combined with FGCP in certain deployment architectures — for example, two FGCP clusters (each with their own primary and secondary) can use FGSP to synchronize sessions between the clusters, providing both intra-cluster failover and inter-cluster session consistency.
