Pre-Reading Story

"The Backup That Never Gave Back"

St. Redmond Medical Center operated a converged network that carried clinical applications, nurse call systems, biomedical device traffic, and administrative computing on a shared infrastructure. The network team had configured VRRP for gateway redundancy on the primary patient-care VLAN — a primary FortiGate with a higher VRRP priority and a backup router sharing a virtual IP that all endpoints used as their default gateway. The configuration had been in place for two years without incident. Every quarterly failover test confirmed that when the primary FortiGate was taken offline, the backup router assumed the virtual IP and traffic continued uninterrupted. The tests passed. The audit checklist was satisfied.

During a scheduled maintenance window to upgrade the primary FortiGate's firmware, the network team powered down the primary unit at 2:00 AM. The backup router became the VRRP master and began forwarding traffic — exactly as designed. The firmware upgrade completed at 3:47 AM. The primary FortiGate was powered back on. It rejoined the network, sent out VRRP advertisements with its higher priority value, and waited to be elected master. It never was. VRRP preemption had been disabled on the primary unit — the configuration parameter that controls whether a higher-priority router can reclaim master status from a lower-priority incumbent had been set to off, intentionally, by an engineer who had done so during initial setup to avoid instability during testing and never changed it back for production. The backup router remained VRRP master for the next three weeks.

The security team discovered the issue during a routine audit six weeks after the maintenance window. The backup router was a legacy device without the hospital's required content filtering profiles, DNS security policies, or IPS signatures. For three weeks, all patient-care VLAN traffic had been forwarded by a device that provided no meaningful security inspection. The audit finding was severe. The remediation required a full policy review, an incident report to hospital administration, and a policy change requiring VRRP preemption status to be verified as part of every maintenance procedure. The lesson was not that VRRP was wrong — it was that a single misconfigured parameter had silently neutered the entire redundancy design.

Overview

VRRP — Standards-Based Gateway Redundancy on FortiGate

The Virtual Router Redundancy Protocol (VRRP) is an IETF-standard protocol (RFC 5798) that allows multiple routers or firewalls to share a single virtual IP address, providing transparent gateway redundancy to hosts on the local segment. End devices configure the virtual IP as their default gateway — they are unaware of which physical device is currently acting as master. The master device responds to ARP requests for the virtual IP and forwards traffic normally. If the master fails, the backup device with the next highest priority takes over the virtual IP and sends a gratuitous ARP to update the network's ARP tables. From the perspective of end hosts, the gateway simply continues to function.

VRRP master election is driven by the configured priority value on each participating device. The device with the numerically highest priority becomes master. If all priorities are equal, the device with the highest IP address on the VRRP interface is chosen. The master sends periodic VRRP advertisement packets at a configurable interval; if backup devices stop receiving advertisements beyond the master-down interval, they initiate an election and the highest-priority backup assumes the master role. The preemption setting determines what happens when a previously-offline higher-priority device comes back: with preemption enabled (the default), it reclaims master status; with preemption disabled, the current master holds its role indefinitely until it fails.

FortiGate's implementation of VRRP has important differences from FGCP. VRRP is a gateway redundancy protocol — it only ensures that one device is responding to ARP for the virtual IP and forwarding traffic. It does not synchronize firewall sessions between devices. When a VRRP failover occurs, all existing TCP sessions are reset because the new master has no session table entries carried over from the previous master. This is the fundamental trade-off of VRRP versus FGCP: VRRP is more flexible and interoperable (it can pair a FortiGate with a non-Fortinet router), but it cannot provide session continuity. VRRP is also useful in deployments where two FortiGates serve different VLANs as masters — VRID-based multi-master configurations let each unit be master for a different group of VIPs simultaneously.
