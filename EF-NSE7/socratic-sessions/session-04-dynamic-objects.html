The Migration That Broke Every Policy

Bridgepoint Financial had 15 branch offices, each running a FortiGate managed from a central FortiManager. Over three years the network team had carefully built a consistent set of firewall policies covering internal server access, application control, and inter-branch connectivity. Every policy that referenced a server used a static IP address object — objects like "Branch-AppServer" mapped to specific IPs like 192.168.1.50 at each site. It was a clean, readable setup. When the CFO approved a cloud migration initiative to move all 15 branch application servers to Azure, the IT director signed off thinking it would be a standard lift-and-shift with a few DNS updates. He had not considered that every server would receive a new IP address — Azure's address space looked nothing like the branch 192.168.x.x ranges.

The migration executed cleanly from an Azure perspective. Servers came online with their new addresses in the 10.220.x.x range. But the moment DNS was cut over at the first branch, applications stopped working for users at that site. The firewall policies still referenced the old IP. Every policy on every FortiGate at every branch that pointed to an application server by static IP address was now pointing at a dead address. The network team mobilized — one engineer per branch, eight-hour marathon of CLI sessions and FortiManager object edits. Four days later, the last branch was restored. Midway through day two, an engineer calculated that the total number of static address objects that needed updating across 15 sites and all their policies was 847.

The post-migration retrospective surfaced the solution that should have been used from the start: FortiManager dynamic address objects. A dynamic object is defined once in FortiManager with a placeholder name. Each FortiGate device — or group of devices — has a metadata variable that maps the placeholder to the real local IP. When the policy is installed, FortiManager resolves the placeholder per-device. During the Azure migration, the team would have updated 15 metadata values in FortiManager and re-installed the policy package. Total time: under ten minutes. The 847 individual object edits would not have been necessary. This session is about understanding how dynamic objects work and why they are the correct tool for multi-site template management.

Overview

The central challenge of multi-site FortiManager management is that the same logical policy — "allow users to reach the application server" — needs to resolve to different real IP addresses at each site. A static address object solves this for one site. For fifteen sites, it means fifteen separate objects and fifteen separate policy rules, or a single shared policy that cannot reflect site-specific addressing. Dynamic objects break this constraint by introducing a level of indirection.

A dynamic address object in FortiManager is defined at the ADOM level with a symbolic name. The object itself contains no IP address — instead, it holds per-device mappings. Each managed FortiGate has a metadata variable (a key-value pair) that provides the actual IP or subnet for that device. When FortiManager installs the policy package to a device, it resolves the dynamic object by reading the device's metadata value and substituting the real address. The FortiGate receives a fully resolved, concrete policy — it has no awareness that the address was abstract in FortiManager. From the FortiGate's perspective, it has a normal address object.

Dynamic objects are particularly powerful in environments where server addressing follows site-local schemes, where cloud migrations change IPs en masse, or where new sites are added frequently. When a new site is provisioned, the administrator creates the device in FortiManager, sets the metadata values for that device, and assigns it to the existing policy package. The new site inherits all policies automatically with the correct site-specific address resolutions. Understanding the relationship between dynamic objects, metadata variables, and the install process is an NSE7 exam topic that tests both conceptual understanding and procedural knowledge.
