The Shortcut That Created a Black Hole

Ironwood Capital Management had completed what appeared to be a textbook ADVPN with BGP deployment across 15 regional offices. The network architect had been thorough: hub and spoke IPsec phase1 configurations included the correct auto-discovery flags, BGP sessions were established between each spoke and the hub using iBGP with the hub acting as route reflector, next-hop-self was configured on the hub's BGP neighbor definitions. After a day of monitoring in a lab environment, the deployment was approved for production. All 15 spoke BGP sessions came up cleanly. All 15 spokes had routing tables showing correct prefixes for all other spoke LANs. Traffic flowed. Shortcuts started forming between active spoke pairs. For about 90 minutes, the deployment looked perfect — and then the help desk began receiving calls about dropped file transfers and failed application sessions between specific office pairs.

The network engineer investigating the incidents noticed a pattern: all failing connections were between spoke pairs that had recently formed shortcuts. Spoke pairs that had not yet formed shortcuts — where all traffic still flowed through the hub — had no issues whatsoever. He ran a route table lookup on Spoke A, which had an active shortcut to Spoke B. The routing table showed Spoke B's prefix 10.20.30.0/24 as active with a next-hop of the hub's ADVPN overlay IP — 192.168.100.1. This was correct at deployment time. The shortcut tunnel between Spoke A and Spoke B was alive: get vpn ike gateway showed the shortcut as established, with Spoke B's overlay IP of 192.168.100.8 as the remote gateway. But the FortiGate was forwarding traffic to 10.20.30.0/24 toward the hub IP 192.168.100.1, not toward 192.168.100.8. The BGP route's next-hop had not updated when the shortcut formed. The hub was receiving that traffic, but its own forwarding table was trying to send it back to Spoke B via the hub tunnel — creating an asymmetric forwarding loop that dropped the sessions.

The root cause was that next-hop-self on the hub had caused all BGP routes to point to the hub overlay IP as next-hop. This was correct behavior before shortcuts existed. But when a shortcut formed between Spoke A and Spoke B, the BGP routing layer had no mechanism to automatically update the next-hop for Spoke B's prefix from "hub overlay IP" to "Spoke B's overlay IP via the shortcut." The FortiGate's ADVPN auto-discovery mechanism handles this via a route update triggered when the shortcut is established — but this requires a specific BGP configuration on the spoke to accept the updated next-hop. The fix involved configuring route-map policies on each spoke to allow next-hop updates from ADVPN shortcut events, and ensuring the hub's BGP configuration was aligned with FortiGate's expected ADVPN+BGP integration behavior. After the fix, shortcut formation and next-hop convergence happened in under two seconds with no session disruption.

Overview

The interaction between ADVPN shortcut formation and BGP route propagation is one of the most nuanced topics in the NSE7 curriculum — and the source of a disproportionate share of real-world ADVPN deployment failures. The core problem is a timing and consistency challenge: BGP routes on a spoke are learned from the hub and carry next-hop attributes pointing to the hub's overlay IP. When a shortcut forms between two spokes, the data plane path changes immediately — traffic can now reach the destination spoke directly. But the BGP routing table does not automatically update its next-hop to reflect the new path. Without intervention, the routing table and the forwarding table are inconsistent: the forwarding plane knows about the shortcut, but the routing plane still points to the hub.

FortiGate's ADVPN implementation addresses this via a mechanism called auto-discovery route updates. When a spoke's ADVPN process establishes a shortcut tunnel, it signals the BGP/routing process to update the next-hop for the destination prefix to use the shortcut's tunnel endpoint rather than the hub. This update propagates into the routing table, ensuring that subsequent traffic follows the shortcut path. The reliability of this mechanism depends on the BGP configuration: if route policies on the spoke filter or modify the BGP route in ways that interfere with the next-hop update, the automatic correction will fail. Understanding exactly which configuration elements enable correct next-hop convergence — and which misconfiguration patterns prevent it — is the focus of this session.

A related design consideration is prefix granularity: whether to advertise spoke LANs as their native subnet (e.g., 10.20.30.0/24) or to advertise a loopback or tunnel endpoint as a /32. In ADVPN+BGP, advertising the actual LAN prefix is the standard approach. Advertising /32 loopbacks has use cases in certain redundancy designs but complicates the next-hop update process because the shortcut forwarding next-hop and the BGP next-hop are different address types. The exam tests understanding of what happens to BGP routes when shortcuts go down as well as when they form: when a shortcut is torn down due to idle timeout, the routing layer must fall back to hub-based next-hops gracefully, and BGP must re-advertise the affected routes with hub next-hops before the shortcut disappears entirely to avoid a black-hole gap during the transition.
