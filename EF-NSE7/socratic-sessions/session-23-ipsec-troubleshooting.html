Session 23 Chapter 07 — IPsec

IPsec Troubleshooting

Debug commands, SA state machines, and the most common IPsec failure points — a systematic approach.

Before You Begin · Real-World Scenario

The Tunnel That Was Up But Dead

Brightway Logistics operated a critical site-to-site VPN between their central dispatch facility and their largest regional sorting hub. The tunnel carried order routing data, driver assignments, and real-time package tracking — without it, sorting operations at the hub ran blind. On a Thursday afternoon, sorting hub staff reported that the order management system had lost connectivity to the central dispatch database. The network operations team pulled up the FortiGate dashboard at the central facility: the VPN tunnel showed green. Phase 1 status: established. Phase 2 status: established. The tunnel was visually indistinguishable from a fully functional connection. The team confirmed the physical WAN link was up. They checked the firewall policy — permit from hub subnet to dispatch subnet, logging enabled. The logs showed no denied traffic.

Three engineers worked the problem for six hours. They verified routing tables on both sides — correct. They checked NAT configurations — no unexpected translation. They tested ICMP from the dispatch FortiGate toward the hub subnet — no response, but ICMP was potentially blocked by hub-side policy so this wasn't conclusive. They rebooted the application server at the hub and the database server at dispatch — no change. They examined FortiAnalyzer traffic logs and found zero traffic in the last four hours on what should have been a continuously active connection. The tunnel appeared UP in the GUI but was passing zero bytes. The senior engineer on the call suggested it might be an application issue rather than a network issue. An application vendor was called in. Two hours later, the application vendor confirmed the connectivity was broken at the TCP level — packets were not arriving at the destination. It was a network problem. The investigation had come full circle.

Finally, at hour six, the senior network engineer ran a command she had not tried yet: diagnose vpn tunnel list. The output showed the IPsec SA — Phase 1 up, Phase 2 entry present — but the packet input and output counters were at zero and had been at zero since the SA was established. She then ran diagnose debug application ike -1 combined with diagnose debug enable and triggered a traffic test. The IKE debug output showed the local FortiGate attempting to use the existing SA to encrypt outbound packets, but the remote peer's IKE daemon had crashed silently hours earlier. The SA entry existed locally but was not honored by the remote side — it had been orphaned. The remote peer was not responding to re-key requests because its IKE process was down. A simple IKE daemon restart on the remote FortiGate — diagnose debug reset followed by clearing the SA — brought the tunnel back in under ninety seconds. The six-hour investigation would have resolved in ten minutes with the right diagnostic command run first.

Overview

IPsec troubleshooting on FortiGate requires understanding both the state machine that governs SA establishment and the specific CLI commands that expose that state. The most dangerous failure mode in IPsec is not a tunnel that is visibly down — that is easy to detect and prioritize. The most dangerous failure mode is a tunnel that appears UP in the GUI while passing zero traffic, as the scenario above illustrates. The GUI tunnel status reflects whether an SA entry exists locally; it does not verify that the remote peer is actively honoring that SA or that traffic is actually flowing. Always verify with packet counters and diagnostic commands, not the dashboard status indicator.

FortiGate provides a layered set of diagnostic commands for IPsec. The diagnose vpn tunnel list command shows all active IPsec SAs with their current packet counters, SA indices, proxy IDs, and lifetime remaining — this is the first command to run when a tunnel appears up but traffic is not flowing. The diagnose vpn ike gateway list command shows IKE Phase 1 state. The diagnose debug application ike -1 command combined with diagnose debug enable provides real-time IKE negotiation output — this is the most powerful troubleshooting tool for Phase 1 and Phase 2 failures, showing exactly what proposals are being exchanged, where mismatches occur, and what error messages the IKE daemon generates. Packet capture (diagnose sniffer packet) on the WAN interface can confirm that ESP-encrypted packets are leaving the FortiGate, verifying that traffic is actually being encrypted and transmitted.

Systematic troubleshooting follows the IPsec state machine from outside in: first confirm the WAN path is reachable (UDP 500 and 4500, ESP protocol 50), then verify Phase 1 negotiation succeeds (IKE SA established), then verify Phase 2 negotiation succeeds (IPsec SA established), then verify traffic is matching the tunnel selector and being encrypted (packet counters incrementing), then verify traffic is arriving at the destination. Each layer has specific failure signatures in the debug output, and understanding what a proxy ID mismatch, a proposal mismatch, or an SA expiry looks like in the IKE debug stream is a core NSE7-level skill.
