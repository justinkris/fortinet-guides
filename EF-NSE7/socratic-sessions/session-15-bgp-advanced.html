The Route Leak That Accidentally Became a Transit ISP

Northfield University had done everything right when they contracted for dual-ISP internet connectivity — ISP-A provided the primary 10Gbps uplink, ISP-B provided a secondary 1Gbps backup link. The network team configured BGP with both providers, received full routing tables (approximately 900,000 routes) from each, and set up a basic policy so that ISP-A was preferred for outbound traffic based on LOCAL_PREF. The design was sensible, the redundancy was real, and for six months it worked exactly as intended. The catastrophic misconfiguration had been dormant the entire time, waiting: neither ISP-A nor ISP-B had outbound prefix-list filters applied in the FortiGate BGP configuration. Northfield was advertising everything it received — including routes from ISP-A — back toward ISP-B, and everything from ISP-B back toward ISP-A.

On the morning of the incident, ISP-B's upstream peering router made a local preference change that briefly made Northfield's path look more attractive for a set of popular content delivery network prefixes. Within seconds, both ISPs began routing significant volumes of internet traffic through Northfield's university network and out the other ISP's link. The 1Gbps secondary link saturated in under a minute. The primary 10Gbps link hit 9.8Gbps — all of it transit traffic belonging to neither the university nor its students. The university's own internet access collapsed entirely. Students in dormitories lost connectivity. Research systems dependent on external APIs began timing out. The NOC phones lit up, but so did the NOC phones at both ISPs, who were seeing unexpected route advertisements from an AS that had no business being a transit network. Major content providers began detecting suboptimal routing and paging their own on-call engineers.

The post-incident review was humbling. The outbound filter that would have prevented the entire event was a prefix-list permitting only Northfield's own assigned /16 — six lines of configuration that had simply never been written. The team had focused on inbound traffic engineering (getting the LOCAL_PREF right, making ISP-A preferred) while completely neglecting outbound route advertisement policy. The BGP path selection attributes — LOCAL_PREF, Weight, AS-path length — are powerful tools for controlling where your traffic goes, but they are irrelevant if you are leaking routes you should never be advertising. This session covers both dimensions: the path selection decision process and the filtering mechanisms that keep BGP advertisements bounded to what you actually own.

Overview

When a BGP router receives the same prefix from multiple peers, it must select exactly one best path to install in the routing table and advertise to other peers. BGP's path selection algorithm evaluates competing paths through a deterministic sequence of attributes — the first attribute that differentiates two paths determines the winner, and subsequent attributes are not consulted. This ordered evaluation is frequently called the BGP decision process or the "best path algorithm." Understanding the order and behavior of each attribute is essential for engineering traffic flow in multi-homed environments.

The decision process proceeds as follows: Weight is checked first — it is a Cisco/Fortinet proprietary value, local to the router, not carried in BGP UPDATE messages, and highest value wins. If Weight is tied, LOCAL_PREF is compared — this is an iBGP attribute that propagates within an AS and is used to influence outbound path selection (which exit point the AS uses to reach external destinations). Highest LOCAL_PREF wins. Next, locally originated routes are preferred over received routes. Then AS-path length is compared — shorter is preferred, which is also the primary BGP loop-prevention mechanism. Origin code follows (IGP > EGP > incomplete). MED (Multi-Exit Discriminator) is then compared, but only between routes from the same neighboring AS — it communicates to an upstream AS which of your ingress links you prefer. Lowest MED wins. Finally, eBGP routes are preferred over iBGP routes, and remaining tiebreakers include router ID and peer IP address.

Route filtering in BGP is implemented through prefix-lists and route maps on FortiGate. A prefix-list matches on IP prefixes (with exact or range matching using the le/ge keywords) and is applied per-neighbor as an inbound or outbound filter. A route map provides more flexible matching — it can match on prefix-list, AS-path access-list, community, and other attributes — and can both permit/deny and modify attributes such as LOCAL_PREF, MED, or Weight. Applying outbound route maps to constrain what you advertise to each peer is fundamental operational hygiene in any BGP deployment.
