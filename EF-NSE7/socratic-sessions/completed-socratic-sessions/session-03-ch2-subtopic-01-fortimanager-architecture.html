FortiManager Architecture

How FortiManager separates what a firewall IS from what it DOES — and why that distinction controls everything about policy deployment at scale.

ADOMs aren't just organisational folders — they are blast radius boundaries with real enforcement.

A misconfigured ADOM scope can let one install command overwrite policies across an entire enterprise. Every deployment decision in this chapter flows from understanding the two-layer architecture inside each ADOM.

Device vs Policy Layers ADOMs Global ADOM Install Operations Retrieve vs Push
💭 THINK FIRST · DEVICE VS POLICY LAYERS

Every FortiGate managed by FortiManager lives in two places simultaneously: the device layer (its identity) and the policy layer (its behaviour). The exam regularly tests whether you know which layer a change lives in — and critically, whether that change pushes to FortiGate automatically or requires a manual install step.

  • A colleague edits a firewall address object in the Policy & Objects section of FortiManager. Ten minutes later, the FortiGate still shows the old value. Is this a bug, and what needs to happen next?
  • You need to change the management IP on a FortiGate. Which FortiManager layer does this configuration belong to, and how is it pushed to the device?
Q1 — MODEL ANSWER
Not a bug. Policy layer changes never push to FortiGate automatically. The change exists only in FortiManager's database until an admin explicitly installs the policy package. The engineer needs to run Install Policy Package or Reinstall Policy to push the updated address object to the FortiGate.
Q2 — MODEL ANSWER
Management IP is a device-specific setting — it belongs to the device layer. It is pushed using Install Device Settings Only or Quick Install. These operations target the device layer exclusively and do not touch the policy package.
SECTION 01

Device Layer vs Policy Layer

Each ADOM contains two databases: the device layer (what the firewall IS) and the policy layer (what it DOES).

images/s1-two-layers.png
Flat pastel illustration, two-panel left/right layout. Left panel labelled "Device Layer" in dark red, contains icons for: network interface, routing table, hostname tag, VPN tunnel. Right panel labelled "Policy Layer" in deep burgundy, contains icons for: firewall rule list, address object, security profile badge, NAT arrow. Bold outlines, minimal text, clean white background with soft shadow divider between panels.

FortiManager models every managed FortiGate as existing in two separate databases inside each ADOM. The device layer holds everything that makes a FortiGate what it is — interface configurations, IP addressing, static routes, BGP/OSPF settings, VPN tunnel definitions, system settings, and log targets. These items are unique per device: Branch-FGT-01 has different interface IPs than Branch-FGT-02, and that difference lives here.

The policy layer holds everything that makes a FortiGate do what it does — firewall policies, address objects, service objects, NAT rules, and security profiles. These items can be shared across many FortiGates via a single policy package, which is the central power of FortiManager. The critical operational difference: device layer changes push immediately when you install device settings, but policy layer changes only reach FortiGate after you explicitly install the policy package. Edits sitting in the policy layer are invisible to FortiGate until that install step occurs.

⚑ NSE7 Exam trap: A policy layer change does not push automatically, even if the changed object is referenced in an active firewall policy. The install step is always required.
LayerWhat lives hereHow it reaches FortiGateAutomatic?
Device LayerInterfaces, routing, system, VPN, logsInstall Device Settings / Quick InstallNo — manual install
Policy LayerFirewall policies, objects, profiles, NATInstall Policy Package / Reinstall PolicyNo — manual install
🧠
MENTAL NOTE
2 layers, 2 install paths: device settings install for the device layer, policy package install for the policy layer. Neither is automatic. Think of the policy layer as a Word document saved on a shared drive — your edits are there, but the printer never gets them until you hit print.

💭 THINK FIRST · ADOMS

ADOMs are FortiManager's way of enforcing administrative and operational separation between groups of devices. The question isn't just "what are they" — it's understanding what happens when you don't use them, and what three specific problems they simultaneously solve.

  • A company has 20 FortiGates across three business units, all added to the default root ADOM. An admin in Business Unit A installs a policy package. What two serious risks does this create?
  • When ADOMs are disabled on FortiManager, what ADOM are you actually working in, and does that mean there is no ADOM structure at all?
Q1 — MODEL ANSWER
Risk 1: No blast radius control — a policy package install in the shared ADOM can target all 20 FortiGates, allowing one admin's action to overwrite policies on devices in other business units. Risk 2: No administrative delegation — there is no way to scope an admin to only their own devices, so any admin can see and modify every device.
Q2 — MODEL ANSWER
When ADOMs are disabled you are still working inside an ADOM — the default ADOM named "root". There is still a full ADOM structure (device layer + policy layer + FortiGuard), but all managed devices share that single ADOM with no separation between them.
SECTION 02

Administrative Domains (ADOMs)

Each ADOM is an isolated management domain with its own device layer, policy layer, and firmware version. The Global ADOM sits above all of them.

images/s2-adoms.png
Flat pastel illustration, bird's-eye node graph. Top node: "FortiManager" in dark red rectangle. Below it, three ADOM boxes side by side (pastel blue, green, orange): "ADOM Root 7.6", "ADOM Site1 7.4", "ADOM Branch 7.2". Each ADOM box contains two smaller stacked rectangles: "Device Layer" and "Policy Layer". Above all three, a separate elevated box: "Global ADOM" in gold. Dashed lines from Global ADOM down to each local ADOM. Bold outlines, minimal text, white background.

An ADOM (Administrative Domain) is a virtual management boundary inside FortiManager. Each ADOM contains its own device layer, policy layer, and set of ADOM functions. Devices in one ADOM are completely isolated from devices in another — an install action in ADOM-A cannot touch devices in ADOM-B. This is not a configuration option; it is enforced by the architecture.

ADOMs solve three problems simultaneously. First, blast radius control: a policy install is scoped to the ADOM, preventing cross-business-unit accidents like the Meridian Financial incident. Second, firmware version isolation: each ADOM has an assigned FortiOS version, allowing DC FortiGates on 7.6 and branch FortiGates on 7.4 to coexist safely on the same FortiManager. Third, administrative delegation: admin accounts can be scoped to specific ADOMs, so a branch team never sees DC policies. When ADOMs are disabled, all devices land in the default root ADOM — a fully functional single ADOM, but with zero separation between devices.

Common misconception: "Disabling ADOMs means there is no ADOM structure." Wrong — you are always working inside an ADOM. With ADOMs disabled, that ADOM is named root.
🧠
MENTAL NOTE
ADOMs solve 3 things: blast radius, firmware isolation, and admin delegation. Even with ADOMs "disabled", you're inside an ADOM called root. Each ADOM carries a firmware version; mixing versions is permitted temporarily for migration but is not a recommended steady state.

💭 THINK FIRST · GLOBAL ADOM

The Global ADOM solves a specific enterprise problem: you need one rule applied to every FortiGate in the organisation, regardless of which local ADOM it belongs to. The exam tests the difference between the two push methods — Assign and Auto-install — which have meaningfully different outcomes.

  • What is the difference between "Assign" and "Auto-install" when pushing a Global policy package to local ADOMs? Which one requires a follow-up manual action?
  • A Global ADOM is running FortiOS 7.6. Which local ADOM firmware versions are compatible with it, and why is the "g" prefix significant?
Q1 — MODEL ANSWER
Assign updates only the policy layer of the local ADOM and flags it as Modified. A manual policy package install is still required to push changes to the FortiGate. Auto-install skips the manual step — it pushes directly to the policy package, the device database, and the FortiGate simultaneously, but it also bypasses the installation preview, so there is no chance to cancel.
Q2 — MODEL ANSWER
A Global ADOM at 7.6 supports local ADOMs at the same version and two minor versions earlier: 7.6, 7.4, and 7.2. The "g" prefix is reserved — FortiManager automatically prefixes all global objects with "g", and no custom object in any local ADOM may start with "g", preventing naming collisions between global and local objects.
SECTION 03

The Global ADOM

The Global ADOM sits above all local ADOMs. Two distribution methods: Assign (policy layer only, manual install needed) vs Auto-install (direct to FortiGate, no preview).

images/s3-global-adom.png
Flat pastel illustration, two-panel left/right showing the two push paths from Global ADOM. Both panels show "Global ADOM" at top in gold. Left panel labelled "ASSIGN": arrow goes to "Policy Layer" box only (highlighted), below it a dotted grey arrow to "FortiGate" labelled "manual install still required". Right panel labelled "AUTO-INSTALL": single bold arrow goes directly through "Policy Layer → Device DB → FortiGate" in one shot, labelled "no preview / no cancel". Bold outlines, pastel palette, white background.

The Global ADOM is a special ADOM that sits above all local ADOMs on FortiManager. Its purpose is to define security policies and objects that must apply across every ADOM in the organisation — a compliance block rule, a mandatory logging policy, or a corporate URL filter. Rather than manually adding these to every policy package in every ADOM, the Global ADOM distributes them automatically.

There are two distribution methods. Assign pushes the global policy package to the policy layer of the local ADOM and flags it as Modified. Nothing reaches the FortiGate until an admin manually installs the policy package. Auto-install bypasses the manual step entirely — it pushes simultaneously to the policy package, the device database, and the FortiGate itself. Crucially, Auto-install also bypasses the installation preview, meaning there is no opportunity to review or cancel the change before it lands on FortiGate. All global objects are automatically prefixed with the reserved letter "g". No custom object in any local ADOM may use this prefix.

⚑ NSE7 — Compatibility rule: A Global ADOM at version 7.6 supports local ADOMs at 7.6, 7.4, and 7.2 (same version + two minor versions earlier). ADOMs older than 7.2 are not compatible.
🧠
MENTAL NOTE
Assign = policy layer only + manual install still required. Auto-install = policy layer + device DB + FortiGate in one shot, but NO preview and NO cancel. The "g" prefix on global objects is reserved — you cannot create any custom object starting with "g" in a local ADOM. Global ADOM at 7.6 supports local ADOMs at 7.6, 7.4, and 7.2.

💭 THINK FIRST · INSTALL OPERATIONS

FortiManager has four distinct install operations. Each targets a different layer, shows (or skips) a preview, and runs (or skips) a wizard. Mixing them up on the exam — particularly using Quick Install when you mean to push policies — is a common costly mistake.

  • A junior engineer wants to push updated firewall policies to 10 branch FortiGates. They choose Quick Install because it sounds fast. What exactly will Quick Install do, and what will it NOT do?
  • What is the key operational difference between "Install Policy Package" and "Reinstall Policy"? Which one pushes more than just policies?
Q1 — MODEL ANSWER
Quick Install pushes device layer settings (interfaces, routing, system config) from the device database directly to FortiGate. It does NOT push the policy package. The firewall policy changes will not be deployed. The engineer needs to use Install Policy Package instead.
Q2 — MODEL ANSWER
Install Policy Package uses a wizard to select the target device and package, then shows an installation preview before committing. Reinstall Policy skips the wizard (device and package are already paired) but still shows a preview. Critically, Reinstall also applies any pending device database modifications — not just the policy package — making it broader in scope than a standard install.

💭 THINK FIRST · RETRIEVE VS PUSH

The direction of data flow is one of the most commonly confused concepts in FortiManager operations. Retrieve and Auto-Retrieve are inbound — they pull from FortiGate into FortiManager. Every install operation is outbound — FortiManager pushes to FortiGate. Mixing up the direction under exam pressure costs marks.

  • An engineer runs Auto-Retrieve on a FortiGate. Does this update the policy package in FortiManager? What exactly does it update?
  • Describe the complete data flow for each operation: Retrieve, Auto-Retrieve, Install Device Settings, Install Policy Package. Which direction does each travel?
Q1 — MODEL ANSWER
No. Auto-Retrieve only updates the device layer database in FortiManager — it captures the current FortiGate configuration and saves it as a new revision. The policy package is not touched. Policy package status remains whatever it was before the retrieve.
Q2 — MODEL ANSWER
Retrieve: FortiGate → FortiManager (inbound) — captures config, saves as new revision, device DB updated only. Auto-Retrieve: same direction, triggered automatically on FortiGate config change. Install Device Settings: FortiManager → FortiGate (outbound) — pushes device layer only. Install Policy Package: FortiManager → FortiGate (outbound) — pushes policy package only.
SECTION 05

Retrieve vs Push — Data Flow Direction

Retrieve and Auto-Retrieve are always inbound (FortiGate → FortiManager). All install operations are always outbound (FortiManager → FortiGate).

images/s5-retrieve.png
Flat pastel illustration, two-panel left/right. Left panel: "FortiManager" box on left, "FortiGate" box on right. Large left-pointing arrow between them labelled "RETRIEVE / AUTO-RETRIEVE" in blue. Small text below arrow: "device DB updated only — policy package unchanged". Right panel: same two boxes. Large right-pointing arrow labelled "INSTALL OPERATIONS" in red. Small text below: "Device layer / Policy package / Both". Bold outlines, minimal text, white background.

Retrieve and Auto-Retrieve are inbound operations — they pull the current configuration from FortiGate into FortiManager. The result is a new revision saved in the device database. Importantly, neither operation touches the policy package. The policy package status before the retrieve is identical to the policy package status after. This is a critical distinction when troubleshooting sync issues.

The difference between the two is timing: Retrieve is manually triggered by an admin. Auto-Retrieve fires automatically when FortiManager detects a configuration change on the FortiGate. Every install operation — Install Policy Package, Reinstall Policy, Install Device Settings, Quick Install — travels in the opposite direction: outbound from FortiManager to FortiGate.

⚑ NSE7 — Direction test: Retrieve always goes FortiGate → FortiManager. Install always goes FortiManager → FortiGate. If an exam question says "Retrieve updated the policy package," that is false.
🧠
MENTAL NOTE
Retrieve = inbound, device DB only, policy package untouched. Auto-Retrieve = same but automatic. All install operations = outbound. You can remember the direction with: "Retrieve pulls, Install pushes." Never mix the arrows — this is a one-point trap on the exam.
