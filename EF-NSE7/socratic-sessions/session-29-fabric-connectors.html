Session 29 Chapter 09 — Security Fabric

Fabric Connectors

SDN and cloud connectors that make firewall policies dynamically aware of your infrastructure.

Before You Begin · Real-World Scenario

The Migration That Made Every Policy Wrong

A SaaS company running a mid-market HR platform had spent 18 months building out what they considered a mature firewall posture. Forty application servers — web tiers, API gateways, database clusters, and background job workers — each had a named IP address object in FortiGate. Firewall policies were built around these objects with real intention: the payment processing cluster could talk to the database cluster on specific ports, the API gateway could reach the web tier, the job workers had no direct internet access. The team was proud of the policy structure. It had taken a security engineer most of a quarter to clean it up from the original flat-network mess, and it was finally documented and sensible. Then the CTO approved a weekend AWS migration.

The migration completed at 2:47 AM on a Sunday. By 6 AM, the DevOps team was getting paged. Marketing servers couldn't reach the database — the policy still referenced the old RFC 1918 address that no longer existed. The payment processing cluster was blocked because its new AWS VPC DHCP address fell into a different subnet than the static object the policy expected. The job workers were stuck because a dependency they needed was at a completely different IP inside the VPC. The on-call engineer logged into FortiGate and found 200 address objects, each containing a static IP that was now wrong. Every policy that had been carefully scoped and documented was referencing addresses that no longer existed in the network. Marketing started calling when their dashboard wouldn't load at 9 AM. Finance escalated when invoicing couldn't process at 10 AM. The firewall team worked through Sunday and into Monday morning manually correcting address objects one at a time.

The post-migration review was uncomfortable for everyone who had spent months on the firewall posture. The fundamental problem was that static IP address objects are brittle by design — they encode a snapshot of infrastructure state that becomes wrong the moment the infrastructure changes. The engineer who had built the address objects had been meticulous, but meticulousness couldn't survive a cloud migration where DHCP hands out addresses from a pool. A Fabric Connector pointed at the AWS API would have resolved this entire class of problem: dynamic address objects keyed to instance tags, autoscaling group membership, or VPC subnet would have updated automatically as each server came online in AWS. The migration would have been transparent to the firewall. Three days of manual remediation work — and the customer-facing outage — could have been avoided entirely.

Overview

Fabric Connectors are integration points that allow FortiGate to pull live data from external systems — cloud platforms, SDN controllers, and threat intelligence feeds — and use that data to dynamically build firewall policy objects. The most common application is dynamic address objects: instead of a static IP address object that an administrator manually maintains, a dynamic address object is keyed to a filter — a tag value, an instance attribute, a security group name — and FortiGate continuously polls the connected platform to resolve which current IP addresses match that filter. When infrastructure changes, the address object updates automatically.

The two major categories of Fabric Connectors are cloud connectors (AWS, Azure, Google Cloud, Oracle Cloud) and SDN connectors (VMware NSX, OpenStack, Nuage). Cloud connectors authenticate to the cloud provider's API using credentials or IAM roles and query resource metadata. An AWS connector, for example, can filter by tag key/value pairs, VPC ID, or instance state. An Azure connector can filter by resource group or tag. The connector polls on a configurable interval and rebuilds the address object's IP list whenever the result changes. Policies referencing these dynamic objects enforce the current state of the infrastructure automatically, with no manual intervention required.

Understanding what happens when a connector loses API access — and how long polling intervals affect responsiveness — is important for operational reliability. A long polling interval means a newly provisioned server might not be reachable through the firewall for several minutes after launch. An unreachable API endpoint raises questions about how existing sessions are handled. These edge cases are part of what the NSE7 exam tests: not just the happy path of connector configuration, but what happens at the boundaries and failure modes.
