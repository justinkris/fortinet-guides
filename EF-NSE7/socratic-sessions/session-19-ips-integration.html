Ten Thousand Alerts Nobody Read

Covenant Health Network operated a regional hospital system across four campuses, each connected back to a central data center through FortiGate appliances. The security team had done diligent work configuring the IPS sensor: it was applied to every internet-facing policy, the signature database was current, and the sensor used a comprehensive profile that covered servers, clients, and known exploits. There was one configuration choice that nobody had questioned in two years of operation: the IPS action was set to "detect" rather than "block." The decision had been made during initial deployment to avoid false positives disrupting clinical systems — a reasonable concern in healthcare. The intent was to review detections and tune before switching to prevention mode. The tuning review never happened.

Over four months, the IPS sensor dutifully logged every signature match to FortiAnalyzer. The log volume was enormous — 400,000 IPS events across the fleet, spanning everything from port scan probes to web crawler fingerprinting. Nobody was reviewing the logs in any systematic way. The alerts were acknowledged as background noise. During the third month, an attacker began exploiting a known Apache HTTP server vulnerability affecting one of the health network's patient portal web servers. The CVE was several months old; a FortiGuard signature existed and was active in the sensor. The IPS engine detected the exploit payload on the first attempt, logged it with a HIGH severity rating, and allowed the session to complete. Then it did the same thing 846 more times over the following six days as the attacker methodically accessed and exfiltrated patient records.

When the breach was discovered — through a patient complaint about unfamiliar insurance claims, not through any internal monitoring — the incident response team pulled the FortiAnalyzer logs within the first hour of investigation. Every exploit attempt was there: timestamped, severity-rated, CVE-identified, source IP logged. The IPS had performed perfectly as a detection system. The single configuration choice — "detect" instead of "block" — was the entire gap between a logged intrusion attempt and a blocked one. The forensic report noted that switching the IPS action to prevention mode required changing one dropdown in the FortiGate GUI. The regulatory response, patient notification, and breach remediation program took eighteen months and cost the health network significantly more than that configuration change would have.

Overview

Intrusion Prevention System (IPS) on FortiGate operates as a deep packet inspection engine that examines network traffic for patterns matching known attacks, protocol anomalies, and exploit signatures. Unlike web filtering and application control, which focus on content policy — what you are allowed to access — IPS focuses on threat detection: identifying traffic that represents an active attack or exploitation attempt, regardless of whether the destination is permitted by policy. IPS can catch exploit payloads inside otherwise-allowed traffic flows, making it the last line of defense within the security profile stack for sessions that web filtering and application control have permitted.

FortiGate IPS uses two complementary detection methods. Signature-based detection matches traffic against a database of known attack patterns — the FortiGuard IPS database contains tens of thousands of signatures covering CVEs, known exploit frameworks, protocol violations, and malware command patterns. Anomaly-based detection (also called rate-based detection) watches for statistical deviations from normal traffic patterns — unusually high connection rates, unexpected protocol frequencies, or traffic volumes that suggest scanning or denial-of-service activity, even when no specific signature matches. The IPS sensor is the object that ties these capabilities together: you define which signatures and anomaly rules are active in a sensor, set the action (detect, block, reset, quarantine), and then apply the sensor to one or more firewall policies.

The operational distinction between detect and prevention mode is central to this session. Detect mode logs matches without taking blocking action — it is useful during initial deployment to identify false positives and tune the sensor before enforcement. Prevention mode blocks matching traffic, resets connections, and can quarantine source addresses. The risk of leaving IPS in detect mode indefinitely is precisely what the scenario above illustrates: detection without action creates a comprehensive audit trail of attacks that succeeded. IPS effectiveness is also directly coupled to SSL inspection — a sensor applied to a policy without SSL deep inspection has no visibility into encrypted payloads, meaning it can only inspect the unencrypted outer traffic metadata for HTTPS sessions.
