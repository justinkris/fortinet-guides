Before You Begin · Real-World Scenario

150 Milliseconds to the Next City

Meadowfield Retail Group operated 60 branch stores spanning four metropolitan areas in the mid-Atlantic United States. The network team had built a clean hub-and-spoke IPsec VPN: every branch FortiGate maintained a permanent encrypted tunnel to the central data center FortiGate in northern Virginia, traffic flowed in, got processed, and flowed back out. It was the textbook architecture — centralized security policy, centralized logging, single-pane firewall management. For branch-to-data-center traffic it worked perfectly. The problem was that branches needed to do something else: they needed to synchronize inventory with each other. Stores in the same metro area shared warehouse pickups. The Philadelphia flagship shared stock data with the four suburban Philadelphia stores. In hub-and-spoke, that inventory traffic did not travel from Philadelphia flagship to Philadelphia suburban directly. It traveled from Philadelphia flagship to the data center in northern Virginia, traversed the hub FortiGate, and bounced back to Philadelphia suburban. Every packet made a 280-mile round trip to exchange data between two stores that were eight miles apart.

The inventory synchronization application had been written by a vendor who assumed LAN-like latency between stores in the same city. Its session timeout was 5 seconds — generous for a LAN, catastrophic for a 150ms round-trip path. The synchronization jobs were failing at a rate of roughly 30% during peak hours, when the hub data center link was also carrying POS authorization traffic, cloud backup streams, and video surveillance uploads. Store managers noticed the failures as ghost inventory: items that were shown available in the warehouse app but had already been picked by another store. The company's inventory shrinkage metric — the delta between expected stock and actual stock — climbed four points in one quarter. Finance flagged it. The network team's response was to upgrade the hub data center link from 500Mbps to 1Gbps. Latency did not change. The failures continued.

A senior network architect brought in to investigate ran a traceroute from a Philadelphia store to its nearest neighbor. The routing path made the problem unmistakably visible: eight hops, crossing the Chesapeake Bay twice on an 8-mile journey. She drew the traffic path on a whiteboard beside a map of the stores — the geographic absurdity was immediately apparent to every manager in the room. The fix was ADVPN: configuring the hub FortiGate as an ADVPN server and each spoke as an ADVPN client so that whenever two spokes needed to communicate directly, the hub could broker a shortcut tunnel between them. Once the shortcut was active, Philadelphia flagship traffic to Philadelphia suburban stopped touching Virginia entirely. Round-trip latency dropped from 150ms to 5ms. The inventory synchronization failure rate fell to zero within the first week of deployment.

Overview

Auto-Discovery VPN (ADVPN) is a Fortinet enhancement to standard IPsec that allows a hub-and-spoke VPN topology to dynamically create direct spoke-to-spoke tunnels — called shortcuts — on demand. In a traditional hub-and-spoke deployment, all inter-spoke traffic is forced through the hub regardless of the physical proximity of the spokes. ADVPN eliminates this constraint: when spoke A needs to reach spoke B, the hub facilitates a shortcut negotiation so that subsequent traffic travels directly between A and B without touching the hub forwarding path. The hub still exists as the permanent anchor of the topology, but it is no longer a mandatory forwarding waypoint for every packet.

Configuring ADVPN requires specific settings on both the hub and spoke FortiGates. On the hub, the IPsec phase1 interface must have set auto-discovery-sender enable configured — this allows the hub to send shortcut offers to spoke FortiGates when it detects traffic between two spokes. Each spoke must have set auto-discovery-receiver enable in its phase1 configuration to accept those shortcut offers. Without both sides aligned, shortcuts will never form. The shortcut tunnel itself is a standard IKEv2/IPsec tunnel but negotiated dynamically at runtime rather than statically pre-configured — once established, it behaves like any other IPsec tunnel in the routing and forwarding plane.

ADVPN requires a dynamic routing protocol to distribute spoke prefix reachability across the overlay network. Static routes cannot adapt fast enough to shortcut formation and teardown. BGP is the strongly preferred choice: the hub acts as a BGP route reflector (or iBGP peer) advertising each spoke's subnets to all other spokes. When a shortcut forms, the routing layer must update next-hops accordingly so that traffic actually flows through the shortcut rather than continuing to route via the hub. This interaction between the IPsec control plane and the BGP routing plane is one of the key design challenges in ADVPN deployments and a primary focus of the NSE7 exam topic.
