The Firewall That Everyone Blamed

A mid-sized manufacturing company had about 800 employees and a straightforward WAN setup: a 1Gbps dedicated fiber circuit from a regional ISP, terminating at a FortiGate that had been in service for four years. For most of those four years, nobody thought about the firewall much. Then the company deployed a new ERP system, added cloud backup for all workstations, and onboarded a video conferencing platform for the sales team — all within the same six-month window. Performance complaints started arriving in the help desk queue: "the internet is slow," "my video calls keep dropping," "the ERP takes forever to sync." The IT manager looked at the FortiGate dashboard and saw CPU at a concerning 60 percent. The conclusion was immediate and unanimous: the firewall is too slow. It needs to be replaced.

The first replacement was a newer FortiGate model with the same performance tier. The slowness persisted. The IT team escalated to the reseller, who recommended a larger model — a significant step up in both hardware specifications and price. The reseller installed it over a weekend. Monday morning, same complaints. The IT manager was now $180,000 into hardware replacements with no improvement in user experience, and the reseller was out of easy answers. The company brought in an independent consultant who had a reputation for quick FortiGate diagnostics. She plugged a laptop into the management port, opened an SSH session, and ran one command: `get system performance status`. The output came back in about two seconds. CPU 12 percent. Memory 34 percent. NP offload rate 88 percent. The FortiGate was doing fine. She scrolled down to the interface utilization section.

The WAN interface was running at 995 Mbps — sustained, consistent, essentially saturated. The consultant asked whether the company had upgraded their ISP circuit when they added the ERP system, cloud backup, and video conferencing. Nobody had thought to. The company had added three bandwidth-intensive workloads to a 1Gbps circuit that was already running at comfortable capacity, and the circuit had quietly become the bottleneck. The firewall had been logging the interface saturation the entire time — it was right there in `get system performance status`. Two FortiGate replacements, months of IT escalations, and $180,000 in hardware spending could have been avoided with a 30-second CLI command. The lesson that the consultant left with the IT manager was simple: performance diagnosis starts with data, and the data is already on the device.

Overview

FortiGate exposes a comprehensive set of performance metrics through its CLI diagnostics. The starting point for any performance investigation is `get system performance status`, which provides a real-time snapshot of CPU utilization (broken down by user space, kernel, and idle), memory usage, uptime, session count, session rate (new sessions per second), and interface utilization for all active interfaces. This single command surfaces most of the data points needed to distinguish between a CPU-bound problem, a memory-bound problem, and a bandwidth-bound problem — the three root causes that cover the majority of FortiGate performance complaints.

For deeper CPU investigation, `diagnose sys top` shows running processes sorted by CPU consumption — equivalent to the Linux `top` command. This reveals whether a specific process (IPS engine, proxy daemon, management daemon) is consuming disproportionate CPU. For session-level investigation, `diagnose sys session list` and `diagnose sys session stat` show session counts, states, and rates. The NP offload rate — the percentage of active sessions currently being processed by the NP hardware rather than the CPU — is a key metric for hardware-accelerated deployments: a low offload rate on a model with NP hardware indicates that something is preventing sessions from being offloaded, and diagnosing why is a direct path to performance improvement.

Traffic shaping adds another dimension to performance analysis. FortiGate supports two shaping modes — per-policy traffic shaping and traffic shaping policies — and diagnosing shaping behavior requires its own set of commands. Understanding which CLI commands expose which metrics, and how to interpret those metrics to identify a specific bottleneck, is both a practical operational skill and a direct NSE7 exam topic. This session focuses on building that systematic diagnostic methodology from the CLI up.
