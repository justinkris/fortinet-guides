Configure IPsec Tunnels

Before You Begin · Real-World Scenario

Policy-Based vs Route-Based: The Three-Day VPN

Vantage Industrial Supply was migrating its data center from a colocation facility to AWS. The network architect assigned to the project had years of FortiGate experience and had built dozens of site-to-site VPN tunnels over his career. Every one of those tunnels had been policy-based — it was the configuration model he had learned first, trusted, and never had reason to revisit. When the AWS VPN Gateway was provisioned, he downloaded the configuration guide, noted the AWS side settings, and began building the FortiGate configuration. Phase 1 came up cleanly. Phase 2 entered negotiation. Then nothing. The AWS console showed Phase 2 stuck in a negotiation loop. The FortiGate showed the tunnel as partially established. Traffic would not pass in either direction.

The engineer spent the first day checking pre-shared key character encoding — a common culprit. He verified encryption algorithms: AES-256 on both sides. He checked DH groups: group 14 on both sides. He verified the Phase 2 proxy IDs matched the AWS-specified local and remote networks. He rebooted both sides. He opened a case with AWS support and waited six hours for a response that confirmed their side was configured correctly per the downloaded guide. Day two began with checking MTU settings, NAT-traversal configurations, and dead peer detection timers. Every parameter matched. The tunnel continued to fail Phase 2. Other engineers were pulled in. Nobody had an answer. The migration project was stalled.

On day three, a Fortinet TAC engineer joined a call. Within five minutes of reviewing the configuration, he identified the fundamental issue: AWS VPN Gateway supports only route-based (virtual tunnel interface) VPN. The FortiGate was configured in policy-based mode, which uses a fundamentally different traffic-handling model — one that is architecturally incompatible with AWS's implementation regardless of how precisely the Phase 1 and Phase 2 cryptographic parameters are aligned. The TAC engineer rebuilt the FortiGate side as a route-based VPN with a tunnel interface in under twenty minutes. The tunnel came up on the first attempt. Three days of investigation dissolved into a configuration paradigm the engineer had simply never encountered before — the difference between policy-based and route-based VPN is not a minor detail, it is an architectural choice that determines interoperability.

Overview

IPsec (Internet Protocol Security) is the dominant framework for building encrypted VPN tunnels between network devices. On FortiGate, IPsec tunnels can be constructed in two fundamentally different architectural modes: policy-based and route-based. In policy-based VPN, there is no dedicated tunnel interface — traffic is matched by a firewall policy with an action of "IPsec" and implicitly routed through the tunnel based on policy match. In route-based VPN, FortiGate creates a virtual IPsec tunnel interface (named vip0, or a custom name) that appears in the routing table like any other interface. Traffic destined for the remote network is routed to that interface via static or dynamic routing entries, and a separate firewall policy permits traffic to and from that interface.

Route-based VPN is the strongly preferred model in modern deployments for several reasons. It integrates cleanly with dynamic routing protocols — OSPF or BGP can run over a tunnel interface just as they would over any physical link. Multiple subnets can be reachable over a single tunnel without modifying Phase 2 traffic selectors. Cloud providers (AWS, Azure, GCP) exclusively support route-based VPN. And troubleshooting is more straightforward because the tunnel interface appears in routing and interface diagnostics alongside all other interfaces. Policy-based VPN is retained for compatibility with older peer devices and specific legacy configurations, but it is increasingly a legacy mode.

Both modes rely on the same underlying IPsec protocol machinery — the IKE negotiation, the Phase 1 and Phase 2 security associations, and the ESP encryption of traffic. Understanding the distinction between the two modes, and knowing which scenarios require route-based, is foundational knowledge for the NSE7 exam and for real-world enterprise VPN deployments. This session also introduces the core IPsec concepts — ESP, AH, IKE protocol numbers, and Dead Peer Detection — that underpin all VPN configurations on FortiGate.
