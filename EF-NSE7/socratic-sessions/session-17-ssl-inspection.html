The C2 That Hid in Plain HTTPS

Meridian Retail Solutions operated 42 franchise locations across three states, all protected by FortiGate appliances at each site. The IT team had done solid work — web filtering was configured, antivirus profiles were active, and the policies were well-documented. What they had not tackled was SSL deep inspection. The decision had been deferred twice: once because of concerns about breaking internal applications, and once because the certificate deployment to workstations felt like a large project. In early autumn, an attacker operating through a supply-chain compromise installed a lightweight C2 agent on a point-of-sale workstation at the flagship store. The agent phoned home via HTTPS to a subdomain of a major cloud hosting provider — domain reputation clean, TLS certificate valid and issued by a public CA. FortiGate checked the certificate, saw nothing wrong, and allowed the connection. The outer envelope was legitimate in every measurable sense.

For six weeks, the C2 agent operated without interruption. It exfiltrated card-present transaction data in small encrypted payloads blended into normal HTTPS traffic streams. The FortiGate logged the sessions dutifully — source IP, destination domain, bytes transferred, policy matched. Nothing flagged. The web filter saw an allowed category. The IPS never triggered because the malicious payload was encrypted inside TLS and the IPS engine only had visibility to the outer flow metadata. The antivirus profile, configured correctly for cleartext flows, had nothing to scan. The 3 GB of customer payment card data moved across the wire in 847 individual sessions over 44 days, each session indistinguishable from normal cloud application traffic at the network layer.

The breach was discovered through a third-party threat intelligence alert — a partner payment processor flagged a cluster of fraudulent card-present transactions that all traced back to Meridian locations. Digital forensics pulled the FortiGate logs and found every C2 session documented, timestamped, and unblocked. The forensic team's conclusion was precise: SSL deep inspection, had it been configured, would have exposed the malicious payload on the first session and the IPS and antivirus profiles would have terminated the connection. The certificate deployment project that had been deferred twice would have taken two days. The breach response, regulatory notification, and card reissuance program took fourteen months.

Overview

SSL/TLS encryption has become the default transport for virtually all web traffic — well over 90% of internet flows are encrypted. This is enormously beneficial for privacy and data integrity, but it creates a fundamental problem for network security inspection: the same encryption that protects legitimate data also conceals malicious payloads, command-and-control communications, and data exfiltration streams from security tools that operate at the network layer.

FortiGate addresses this with SSL deep inspection, also called full SSL inspection or SSL/TLS man-in-the-middle inspection. In this mode, FortiGate intercepts the TLS handshake between the client and the destination server, establishes two separate TLS sessions — one with the client, one with the server — decrypts the payload in the middle, applies all configured security profiles to the cleartext content, then re-encrypts and forwards it. To the client, FortiGate presents a dynamically signed certificate using its own CA, which is why that CA must be trusted on client machines. Certificate inspection is the lighter alternative: FortiGate does not decrypt the payload but inspects only the certificate metadata (CN, SAN, issuer, expiry) to detect anomalies or policy violations without full visibility into the content.

SSH inspection operates similarly for SSH sessions: FortiGate can inspect SSH tunnels to detect protocol misuse (such as port forwarding or X11 forwarding) and can apply logging or blocking controls based on SSH command content. Both SSL and SSH inspection have performance implications — decryption and re-encryption require CPU cycles — and there are categories of traffic (banking sites, health portals, certificate-pinned apps) that should be exempted to avoid breaking functionality or creating privacy concerns. Understanding when to inspect, when to exempt, and how to communicate the deployment to users is a core NSE7 competency.
