Session 05 Chapter 02 — Central Management

Scripts on FortiManager

Automate mass configuration changes across hundreds of FortiGates in minutes — safely and auditably.

Before You Begin · Real-World Scenario

200 Devices, 3 Weeks, and 40 Typos

Eastbrook Health Network ran 200 FortiGate firewalls across hospitals, clinics, and administrative offices in four states. When a new compliance policy mandated that all devices migrate to a centralized NTP server at 10.10.200.10 and adopt a new DNS search suffix of "corp.eastbrook.local", the network operations team estimated the change would take two weeks if they were efficient. The senior network administrator assigned the task to three junior engineers working in rotation. Their tool of choice was what they knew: SecureCRT with a script that opened SSH sessions sequentially and typed commands. It worked. Mostly.

Three weeks later — one week over the original estimate — a compliance audit scanned all 200 devices for the NTP configuration. Forty devices had an incorrect NTP server address. Some had "10.10.200.100" — a trailing zero had slipped in. Six had "10.10.200.10.0" — a period where there should not have been one. Twelve devices had an incorrect DNS suffix: "corp.eastbrook.local " with a trailing space, which caused DNS lookups to silently fail in ways that took two more weeks to diagnose. The engineers had been careful. They had cross-checked their work. But manual CLI entry at scale produces errors — it is not a character flaw, it is a statistical certainty. In a 200-device environment, even a 95% accuracy rate produces 10 misconfigured devices.

The administrator who reviewed the audit report pulled up FortiManager and spent 45 minutes writing the corrective CLI script: four lines of FortiOS config syntax, tested against one device, then run against all 200 simultaneously through FortiManager's script engine. Every device received the exact same byte-for-byte command sequence. The execution log confirmed success on 198 devices and flagged 2 with connectivity issues — those 2 were addressed individually. Total time to correct 40 devices and validate all 200: under two hours. This session is about understanding how FortiManager scripts work, their execution targets, and the safeguards that make them an appropriate tool for production changes — not a dangerous shortcut.

Overview

FortiManager scripts provide a mechanism to execute FortiOS CLI commands across one or many managed devices from a central point. A script is a text file containing standard FortiOS CLI syntax — the same commands you would type in a device console, written once and stored in FortiManager. Scripts can be run against a single device, a device group, or all devices in an ADOM. They introduce consistency, auditability, and speed that no manual process can match at scale.

The critical concept for NSE7 is the run target. When you execute a script in FortiManager, you must choose where it runs: against the Device Database (updates FortiManager's stored configuration without touching the live device), against the Policy Package (modifies the central policy store, which must then be installed), or directly against the Remote Device via CLI (executes commands on the live FortiGate immediately, bypassing FortiManager's change workflow). The choice of run target determines whether the change enters the managed configuration or bypasses it entirely — with significant implications for audit trails and consistency.

Scripts are not limited to one-off corrections. Script groups allow multiple scripts to be bundled and run in sequence, enabling complex multi-step automation. The FortiManager approval workflow — available in environments with change control requirements — can require that scripts be reviewed and approved before execution. Every script run generates an execution log entry recording the initiating administrator, timestamp, target devices, and per-device success or failure. For regulated environments like healthcare and finance, this audit trail is a compliance asset. Understanding these execution mechanics, the risk model of the Remote Device target, and the approval workflow is the focus of the NSE7 exam objectives for this subtopic.
