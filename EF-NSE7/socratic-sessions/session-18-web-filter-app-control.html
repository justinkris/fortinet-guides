The Tunnel That Bypassed Everything

Ridgecrest Unified School District had deployed FortiGate appliances across all twelve of its campuses after a school board directive to restrict student internet access during school hours. The IT team built a comprehensive web filtering policy: social media blocked, gaming sites blocked, adult content blocked, video streaming restricted to educational channels. The deployment was praised at a board meeting. Teachers reported fewer distractions. The IT director felt confident the policy was working. Then, about three weeks into the semester, a student in the district's largest high school discovered an application called Psiphon — a circumvention tool originally designed for use in countries with state-controlled internet. Psiphon wrapped all outbound traffic in standard HTTPS connections to IP addresses hosted across commercial cloud providers. From the FortiGate's perspective, the traffic looked identical to normal cloud application usage: valid TLS, port 443, well-known hosting provider IP ranges.

Without application control configured to identify the Psiphon protocol's behavioral signature — the specific connection patterns, handshake sequences, and traffic cadence that distinguish it from legitimate HTTPS — the FortiGate had no mechanism to detect or block it. The web filter category check passed because the destination was a cloud host with no negative reputation. The student posted a walkthrough video to a private group, and within four days the workaround had spread peer-to-peer across the district's student population. IT began receiving complaints from teachers about students accessing restricted content, but the FortiGate logs showed only normal HTTPS traffic. The policy appeared compliant in every dashboard view. For three months, roughly 500 students had unrestricted internet access through a tunnel the security appliance could not see.

The resolution required adding an application control profile with tunneling and circumvention application signatures enabled, combined with SSL deep inspection so FortiGate could inspect the actual traffic content rather than relying solely on outer metadata. The lesson was precise: web filtering by URL category alone protects against direct access to known bad sites, but it is fundamentally bypassed by any application that wraps traffic in a legitimate-looking protocol. Application control addresses the second layer — identifying what the traffic actually is, regardless of what port or destination it uses. The two profiles are complementary, not interchangeable, and both are necessary for a complete content filtering posture.

Overview

Web filtering and application control are two distinct but complementary security profiles in FortiGate, and understanding where each operates — and where each fails — is essential for designing an effective content security posture. Web filtering primarily operates on URLs and domain names: it queries the FortiGuard URL database, assigns a category to each requested URL, and applies a permit, block, or monitor action based on policy. The FortiGuard database contains hundreds of millions of categorized URLs across 90+ categories, updated continuously by Fortinet's threat research teams.

Web filtering can run in two inspection modes. In proxy mode, FortiGate acts as an explicit or transparent proxy, fully buffering HTTP and HTTPS requests before applying inspection — this gives the most complete visibility and enables features like safe search enforcement. In flow mode, FortiGate inspects the traffic stream without buffering, offering better performance at the cost of some inspection depth. Application control operates differently: instead of examining URLs, it uses deep packet inspection to identify applications by their traffic signatures — the specific byte patterns, protocol behaviors, and connection characteristics that uniquely identify applications like Skype, BitTorrent, or Psiphon, regardless of what port or protocol they attempt to use.

The interaction between the two profiles matters operationally. A web filter might allow a request to a cloud hosting domain (reputation clean, category: technology) while application control identifies the application as a circumvention tool and blocks it. When both profiles are applied to the same policy, FortiGate evaluates both — the most restrictive action wins. Combined with SSL deep inspection, which provides the cleartext payload necessary for both profiles to operate on encrypted traffic, the three together form a comprehensive content and application control stack. Without SSL inspection, both web filtering and application control are limited to what is visible in the outer TLS metadata.
