Session 14 Chapter 05 — Dynamic Routing Protocols

BGP Fundamentals

Autonomous systems, peer relationships, and path-vector routing — why BGP is the protocol that runs the internet.

Before You Begin · Real-World Scenario

The Next-Hop That Went Nowhere

Meridian Financial Group operated two data centers — one in Dallas, one in Chicago — connected by a pair of dark fiber circuits managed by a colocation provider. The network architect had designed a clean iBGP mesh between the two sites to exchange internal service routes and ensure failover paths were always current. Each FortiGate at each DC ran BGP and peered with its counterpart across the fiber. The deployment was completed on a Friday afternoon, the BGP sessions came up showing Established, routes were exchanged, and the team called it done. The architecture review on paper looked correct: same autonomous system number on both sides, TCP session established, UPDATE messages flowing. What was missing was a single line of configuration — and it would cost the company 36 hours of intermittent application failures before anyone found it.

By Monday morning the application teams were reporting connection timeouts between the two data centers. The pattern was inconsistent: some services worked, some didn't, and the failures shifted throughout the day. The help desk logged over 80 tickets across two days. Network operations confirmed BGP sessions were up on both sides. Ping tests between known hosts worked. Traceroutes showed reasonable paths. The on-call engineer increased logging verbosity and ran packet captures but the traffic appeared to be routing — at least, the routing table showed the right prefixes. Only when a senior engineer ran detailed path verification did the truth emerge: the routes were present in the BGP table, but the next-hop IP addresses were unreachable from the receiving side. Chicago's FortiGate had routes pointing to a next-hop that only existed on Dallas's external ISP link interface — an IP that Chicago had no way to reach directly.

The root cause was the iBGP next-hop behavior. When Dallas's FortiGate received a route from its external BGP peer and passed it to Chicago via iBGP, it preserved the original next-hop — the external peer's IP address on Dallas's upstream link. Chicago's FortiGate dutifully installed the route but could not resolve the next-hop, so the route was present but inactive for forwarding purposes. The fix was to enable next-hop-self on both iBGP peers, which causes a router to rewrite the next-hop to its own loopback or peer address before advertising to iBGP neighbors. A two-minute configuration change. This session covers the iBGP vs eBGP distinction, next-hop behavior, full-mesh requirements, and the operational mechanics of BGP peering on FortiGate — the concepts that prevent this kind of invisible, hard-to-diagnose failure.

Overview

BGP (Border Gateway Protocol) is a path-vector routing protocol and the only EGP (Exterior Gateway Protocol) in widespread use today. Unlike OSPF, which builds a topology map and computes shortest paths, BGP exchanges reachability information annotated with attributes — and makes routing decisions based on policy applied to those attributes. BGP is designed to interconnect separate administrative domains called Autonomous Systems (ASes). Each AS is assigned a unique AS number (ASN) — public ASNs are assigned by IANA/RIRs for internet-facing use, while private ASNs (64512–65534 for 16-bit, 4200000000–4294967294 for 32-bit) are used internally. BGP runs over TCP on port 179, which means it relies on IP reachability before a session can form.

BGP exists in two forms. eBGP (external BGP) runs between routers in different ASes — this is how internet service providers exchange routes with each other and with customer networks. iBGP (internal BGP) runs between routers within the same AS — used when multiple BGP-speaking devices inside one AS need to share BGP-learned routes. The critical distinction is that iBGP does not modify the next-hop attribute when advertising to iBGP peers (by default), which requires that iBGP peers be able to independently resolve those next-hops — or that next-hop-self be configured. Another iBGP rule: a router will not re-advertise an iBGP-learned route to another iBGP peer (the split-horizon rule for iBGP), which requires either a full mesh of iBGP sessions between all iBGP speakers, or a route reflector architecture to avoid the full-mesh scaling problem.

On FortiGate, BGP is configured under the routing protocol section. A neighbor statement defines each BGP peer by IP address and remote AS number. Routes are injected into BGP either via a network statement (which activates a prefix if it exists in the routing table) or via redistribution from another protocol. FortiGate supports standard BGP attributes including LOCAL_PREF, MED, and AS-path manipulation through route maps, and supports both route reflector client and server configurations for iBGP scaling. Understanding the BGP finite state machine — the sequence of states a session passes through from Idle to Established — is essential for diagnosing peering failures.
